# Один поиск — два мира: как объединить платформенные и личные знания

У нас в IWE есть MCP-сервер для поиска по знаниям. Он работает: 5400 документов, гибридный поиск (вектора + ключевые слова), 11 источников. Бот отвечает на вопросы, Claude Code находит нужные файлы в Pack. Всё хорошо — пока платформой пользуется один человек.

А что если пользователей станет сто? Тысяча? У каждого — свои Pack-репозитории с доменными знаниями. Врач формализует медицинские протоколы, инженер — стандарты проектирования, предприниматель — бизнес-модели. Куда это всё класть?

## Проблема: чьи данные на чьём сервере

Первый инстинкт — multi-tenant база. Один Neon, колонка `tenant_id`, данные всех пользователей рядом. Просто, быстро, работает. Именно так устроены почти все SaaS.

Но Pack — это не заметки в Notion. Это формализованное доменное знание: архитектуры, методы, различения, failure modes. По сути — интеллектуальная собственность. Хранить чужие бизнес-секреты на своём сервере — это:

- **Trust barrier.** «Я должен доверить вам свои конкурентные преимущества?»
- **GDPR-ответственность.** Платформа становится data processor. Бэкапы, шифрование, право на удаление, уведомления об утечках.
- **Масштаб за наш счёт.** 1000 пользователей × 1000 документов = миллион записей в нашем Neon. Мы платим за хранение чужих данных.

Оценка по нашим 7 характеристикам (ЭМОГССБ): 8.7 из 10. Безопасность — всего 7. Не годится.

## Решение: BYOB — Bring Your Own Backend

Паттерн из мира инфраструктуры: платформа даёт код, пользователь даёт хранилище. Как Obsidian Sync — приложение бесплатное, а где хранить заметки — решаешь сам.

Разделяем знания на два контура:

**L2 Platform (наш, remote)** — платформенные знания: принципы (ZP, FPF, SPF), платформенные Pack, курсы, руководства. Это публичное знание экосистемы. Живёт на Cloudflare Workers + Neon. Мы управляем, обновляем, гарантируем доступность.

**L4 Personal (пользовательский, BYOB)** — его Pack-репозитории, его DS-репозитории, его заметки. Живёт на его Neon / Supabase / SQLite. Мы не видим, не храним, не отвечаем.

А между ними — **Knowledge Gateway**. Локальный процесс на машине пользователя. Принимает запрос `search("как работает X")`, параллельно шлёт в L2 (remote) и L4 (local), мержит результаты по score, возвращает единый ответ. Пользователь не знает и не думает, откуда пришёл результат.

```
Claude Code → Knowledge Gateway (локальный)
                 ├─ L2: Platform MCP (remote, наш)
                 └─ L4: Personal MCP (его Neon/SQLite)
              merge by score → единый ответ
```

## Что это даёт

**Пользователю:**
- Его знания не покидают его инфраструктуру. Zero trust.
- Один `search` — и платформенные принципы, и личные Pack в одном ответе.
- SQLite-вариант: вообще ничего не регистрировать, всё локально.

**Платформе:**
- Нулевая ответственность за чужие данные. Нет GDPR-обязательств за L4.
- Бесплатный горизонтальный масштаб: каждый пользователь платит за своё хранилище (или не платит, если SQLite).
- Единый код: один `KnowledgeBackend` interface, три реализации (Neon, Supabase, SQLite).

**Setup для пользователя:**
```bash
# В setup.sh шаблона IWE
echo "Выберите хранилище для ваших знаний:"
echo "  1) Neon (рекомендуется)"
echo "  2) Supabase"
echo "  3) Локальное (SQLite)"
# → init-schema → первичная индексация → готово
```

ЭМОГССБ: 9.1 из 10. Безопасность — 10. Масштабируемость — 10. Единственный компромисс — обучаемость (8): нужно завести аккаунт в Neon или Supabase. Но SQLite-вариант снимает и это.

## Различение: BYOB ≠ Managed

Это архитектурное различение, которое стоит запомнить:

| BYOB | Managed |
|---|---|
| Данные на ресурсах пользователя | Данные на ресурсах платформы |
| Платформа даёт код | Платформа даёт сервис |
| Trust = 0 | Trust > 0 |
| GDPR: пользователь отвечает | GDPR: платформа = data processor |

**Тест:** данные пользователя покидают его машину/аккаунт? Да → Managed. Нет → BYOB.

Для платформы развития, где главный актив пользователя — его формализованное знание — BYOB не просто предпочтительнее. Это единственный архитектурно честный выбор.

## Что дальше

Сейчас это ADR-018 v2 в архитектурном плане платформы. Следующий шаг — реализация: выделить L2 из текущего knowledge-mcp, написать Backend interface, собрать Knowledge Gateway. Первый пользователь — я сам: мои личные источники мигрируют из общего Neon в локальный L4.

Если вы проектируете платформу, где пользователи приносят своё знание — подумайте про BYOB. Хранить чужие секреты — дорого во всех смыслах.
