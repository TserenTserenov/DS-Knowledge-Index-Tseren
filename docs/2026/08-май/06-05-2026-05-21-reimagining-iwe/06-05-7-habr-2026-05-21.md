# Runtime / Application split в агентных системах: как строить дистрибутив поверх LLM

Когда разные команды говорят «мы строим ИИ-инструмент», они строят принципиально разные вещи: кто-то агентный runtime, кто-то контентный слой, кто-то интеграцию через MCP. Путаница возникает не от незнания предметной области, а от отсутствия общей системы слоёв, которая бы разделяла эти три вещи. В экосистеме Linux эту проблему решили разделением на ядро, дистрибутив и приложения. В агентных системах мы сейчас проходим тот же путь.

## Восемь слоёв агентной архитектуры

| Слой | Назначение | Типичные реализации | Ответственность |
|------|-----------|-------------------|-----------------|
| 0. Базовая модель | Inference, capabilities | Claude, GPT-4, Gemini | Провайдер |
| 1. Агентный runtime | Оркестрация, управление памятью, очередь задач | LangChain, LlamaIndex, собственный оркестратор | Команда |
| 2. Инструментальный протокол | API для tool calling | MCP (Anthropic), Function Calling (OpenAI) | Провайдер / стандарт |
| 3. Интерфейс-хост | UI и точка входа агента | Claude Code (CLI), VS Code ext, Telegram bot | Провайдер или команда |
| 4. Дистрибутив | Набор решений: как жить с этим стеком | CLAUDE.md, hooks, skills, Pack-система | Команда / автор |
| 5. Контент-слой | Доменные знания, пакеты, программы, цифровой двойник | Pack-репозитории, knowledge bases | Предметная команда |
| 6. Персональный инстанс | Конфигурация под конкретного пользователя | Personal Pack, user preferences, история | Пользователь |
| 7. Экосистема | Сообщество, sharing, маркетплейс | GitHub, форумы, plugin registry | Сообщество |

Ключевое разделение: **слои 0-3** принадлежат провайдерам или стандартам. **Слои 4-7** строите вы.

## Что такое дистрибутив в этом контексте

Ubuntu — это не ядро Linux. Ubuntu — это набор решений о том, как жить с ядром: какой пакетный менеджер, как настроена безопасность по умолчанию, какие утилиты включены в базовую установку. Ubuntu использует ядро через стабильный интерфейс (syscall ABI) и не зависит от конкретной версии ядра, только от этого интерфейса. Именно поэтому Ubuntu можно обновить и перенести на другое железо без полного переписывания.

ИИ-дистрибутив работает по той же логике. Это набор решений о том, как работать с LLM в конкретном контексте:

- **Протоколы сессии** — как открывается и закрывается рабочая сессия, что фиксируется при открытии, что при закрытии
- **Управление памятью** — какие факты переживают закрытие сессии, где хранятся, как индексируются, как устаревают
- **Набор инструментов** — какие MCP-серверы подключены, как конфигурируются, с какими разрешениями запускаются
- **Форматы артефактов** — как именуются файлы, какая структура репозиториев, какие frontmatter-поля обязательны
- **Роли и контексты** — какие системные промпты активируются в каких ситуациях, как переключаются роли

Ключевое свойство дистрибутива: он независим от конкретного хоста (слой 3). Если сегодня агент запускается через Claude Code CLI, а завтра через VS Code extension, дистрибутив должен работать в обоих случаях. Если это условие не выполняется — это не дистрибутив, а конфигурация конкретного инструмента.

## Runtime-цикл как спецификация

Типичный runtime-цикл агентной сессии состоит из трёх фаз:

```
OPEN
  → git pull (синхронизация репозиториев)
  → load context (MEMORY.md, активные РП, конфиг ролей)
  → execute open-protocol (Day Open / Session Open)

WORK
  → agent calls tools via MCP
  → results written to files / DB
  → intermediate states committed

CLOSE
  → execute close-protocol
  → git add <specific paths> && git commit && git push
  → update MEMORY.md (статусы, новые факты)
  → sync all touched repos
```

Большинство ИИ-дистрибутивов существуют как набор скриптов и промптов, но не как контракт между слоями. Проблема проявляется при смене хоста: часть логики цикла написана под специфику конкретного интерфейса (например, Claude Code CLI), и при переходе на другой интерфейс эта логика ломается.

Правильный дистрибутив специфицирует runtime-цикл как интерфейс: `open(context) → work(task) → close(artifacts)`. Хост реализует транспорт. Дистрибутив реализует семантику каждого этапа.

## Текущий разрыв и ближайшие задачи

Если честно описать состояние сейчас: дистрибутив в четвёртом слое уже есть (протоколы, Pack-система, hooks, роли), но он слишком тесно связан со слоем 3 (Claude Code). Это означает: изменения в Claude Code требуют ручного рефакторинга протоколов.

Две задачи, которые устраняют этот разрыв:

**Задача 1: явный контракт между дистрибутивом и хостом.** Формализовать, что именно хост должен поддерживать: вызов open/work/close, доступ к файловой системе через определённый интерфейс, передачу контекста в стандартном формате. После этого один и тот же дистрибутив может использоваться с разными хостами через адаптеры.

**Задача 2: runtime (слой 1) как отдельный компонент.** Сейчас оркестрация агентов встроена в Claude Code. Выделение отдельного runtime-слоя (Hermes) позволяет: запускать агентов автономно без интерактивного чата, координировать нескольких агентов через явный протокол, тестировать поведение дистрибутива в изоляции от конкретного хоста.

## Что не нужно путать

**MCP (слой 2) не является частью вашего дистрибутива.** Вы пишете MCP-серверы, но протокол вам не принадлежит. Если Anthropic изменит MCP, вам нужно адаптироваться. Это предсказуемая зависимость, как зависимость от версии ядра.

**Claude Code (слой 3) — один из возможных хостов, не ваш продукт.** Если дистрибутив строится только для Claude Code, он fragile: любое изменение в Claude Code требует переписывания. Дистрибутив должен знать о хосте ровно столько, сколько нужно через контракт, и не больше.

**Контентный слой (слой 5) — это не часть дистрибутива.** Программы развития, доменные знания, персональные профили пользователей — это приложения поверх дистрибутива. Граница между слоями 4 и 5 требует явного решения. Если дистрибутив «знает» о конкретном контентном слое, он теряет универсальность.

---

Итог: если вы строите что-то поверх LLM и хотите устойчивость при смене провайдера, интерфейса или масштабировании, стоит начать с вопроса: на каком слое из этих восьми я строю? Дистрибутив (слой 4) — это не самый сложный слой для реализации, но именно он определяет, будет ли вся система работать при изменениях в нижних слоях.
