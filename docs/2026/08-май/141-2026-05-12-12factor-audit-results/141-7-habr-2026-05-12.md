# Когда `git push` ничего не деплоит: 12-factor аудит 28 production-сервисов за один день

> Срез того, что у меня получилось за полгода активной разработки AI-агентной системы — от ботов на Railway до edge-функций на Cloudflare Workers. Аудит по [12 факторам Heroku](https://12factor.net/), полная матрица 28 сервисов × 12 факторов и жёсткое заключение ИИ-критика в конце.

## TL;DR

- 28 production deployment units (думал, что 10)
- 336 ячеек compliance-матрицы (28 × 12)
- **155 ✅ (46%), 71 ⚠️ (21%), 33 ❌ (10%), 74 N/A (22%), 3 🟡 (1%)**
- 0 security-критичных нарушений
- Худший фактор: **F5 BRR — 20 из 28 в красной зоне** (15 сервисов без CI deploy)
- Лучший фактор: **F6 Stateless — 0 нарушений** (готово к масштабированию)
- Время: 12 часов фактической работы vs бюджет 60 часов

## Что проверял

Production runtime AI-агентной экосистемы:

- 2 Telegram-бота на Python (aiogram 3.x) + Railway
- 6 background workers на Railway (event-poller, projection-workers, activity-hub, payment-registry)
- 11 Cloudflare Workers (TypeScript) — MCP-серверы, gateway, payment, observability
- 6 autonomous agents (cron-driven на tsekh-1)
- 1 локальный gateway (Node.js MCP), OAuth Hydra (Ory SaaS), CRM, backup-инфра, статичный сайт (Nomad)
- Admin-скрипты (Flyway SQL migrations для Neon)

## Как делал аудит

Подход линейный — одна фаза на фактор. 12 phases × 0.5-3h каждая. Для каждого фактора:

1. Inventory: grep по коду, проверка Dockerfile/wrangler.toml/manifest/config
2. Заполнение ячейки матрицы со статусом (✅/⚠️/❌/N/A/🟡)
3. Запись нарушений в журнал со ссылкой на сервис и описанием

Trust-but-verify в две стадии:

1. Sub-agent (Sonnet) с эталоном 12factor.net в изолированном контексте — ищет противоречия
2. Independent reviewer (тоже Sonnet, cold context) — финальный аудит перед публикацией

Без двух стадий verify первичный отчёт содержал бы false-green.

## Главные находки

### F5 BRR — 15 сервисов без CI deploy

Самая жёсткая находка пришла случайно, на фазе F9 (Disposability). Решил посмотреть env vars Railway-воркера. Нет `RAILWAY_GIT_COMMIT_SHA`. Ни в одном из пяти.

```bash
$ railway run env | grep RAILWAY_GIT
# (empty)
```

Deploy history тоже подозрительная — все записи `reason: "deploy"/"redeploy"` (manual triggers), не `"github"`. Через MCP к Railway API:

```python
deployments = list_deployments(service="aist_bot_newarchitecture")
# all entries: reason="deploy", ignoreWatchPatterns=true
```

Это значит — `wrangler deploy` запускается с локальной машины, не из CI. Последний successful deploy одного из workers — 28 апреля. Сегодня 12 мая. Между ними две недели коммитов, которых в проде нет.

Поднял на следующий уровень: а Cloudflare Workers? У них же стандарт — GitHub Actions с `cloudflare/wrangler-action`. Проверил `.github/workflows/` в 10 репозиториях:

```bash
$ ls .github/workflows/
secret-scan.yml
security.yml
# нет deploy.yml
```

В 4 из 10 — только secret-scan + security workflows. В 6 — нет `.github` директории вообще. **Ни один CF Worker не имеет CI deploy.** `wrangler deploy` запускается локально с dev-машины.

Итого: 5 Railway + 10 CF Workers = **15 production-сервисов без git→deploy linkage**.

Что это значит технически:

- Railway даёт immutable image digest (SHA-256), CF Workers — immutable V8 snapshot с `version_id`. То есть artifact immutable есть.
- Но связи `artifact ↔ git commit SHA` нет. Нельзя сказать «в проде commit `abc123`».
- Rollback возможен только через Railway/CF dashboard к предыдущему version_id, не к конкретному git commit.
- При security-инциденте: «какой код в проде?» — ответ «надо открыть laptop того, кто последний деплоил».

В матрице это понизило F5 для 15 сервисов с ✅ до ❌, и F1 (Codebase) — с ✅ до ⚠️ («один код, много deployments из одного commit» нарушено, потому что production не привязан к commit).

### F6 Stateless — 0 нарушений

Тут наоборот, приятно:

- Telegram-бот переехал с `MemoryStorage` на `PostgresStorage` (FSM-state в БД, не в памяти процесса) — multi-replica safe
- Все 4 Railway worker'а используют DB-cursor с per-domain isolation:

  ```python
  # multi-domain-projection-worker
  async def advance_cursor(domain: str, new_position: int):
      # atomic CAS, multi-replica safe
      await conn.execute(
          "UPDATE processed_events SET cursor = $2 "
          "WHERE projection_name = $1 AND cursor < $2",
          domain, new_position
      )
  ```

- CF Workers stateless by design — нет DurableObjects, module-level state только per-request
- Batched flush с shutdown handler — при SIGTERM cursor успевает записаться в БД

19 из 28 — ✅, ни одного ❌. Архитектура готова к R1→R2→R3 без рефакторинга stateful-частей.

### F8 Concurrency — single-replica контракт через advisory_lock

W2 (event-poller к LMS) и W3 (multi-domain projection) — single-replica de-facto, но контракт не был задокументирован. Случайный `railway scale 2` сломал бы event-ingestion дублями.

Закрыли через `pg_try_advisory_lock` на shared learning DB при старте процесса:

```python
async def acquire_single_replica_lock():
    lock_key = 420220  # стабильный hash от service name
    acquired = await conn.fetchval(
        "SELECT pg_try_advisory_lock($1)", lock_key
    )
    if not acquired:
        logger.error("Another replica is running, exiting")
        sys.exit(75)  # EX_TEMPFAIL — Railway/systemd retry
    logger.info(f"acquired single-replica advisory lock (key={lock_key})")
```

Лок автоматически освобождается при закрытии connection (asyncpg pool shutdown). Дешёвый и надёжный паттерн для будущих stateful Railway workers.

### F9 Disposability — все production workers готовы

- Bot + W2/W3/W4: явный SIGTERM handler через `loop.add_signal_handler(signal.SIGTERM, stop_event.set)` + graceful drain of asyncio tasks
- W3/W4: batched CursorCache с flush в `finally` — при kill cursor успевает записаться
- CF Workers: <100ms cold start (V8 isolates), request-isolated — SIGTERM-концепция не применима
- Idempotency через atomic cursor advance: crash mid-batch безопасен, события не теряются

Cold start времена:

| Сервис | Cold start |
|--------|-----------|
| CF Workers | <100ms (V8 isolate) |
| Railway bot | 3-5s (pool warmup через `asyncio.gather()`) |
| Railway workers | 1-3s (DB pool init + advisory_lock) |

Все < 30s порога 12factor.net.

## Что вышло хорошо

- **0 security-критичных нарушений.** За полгода ad-hoc разработки не закатил ни одного hardcoded токена в код. Проверил grep'ом всех `.py`/`.ts`/`.js` файлов HEAD-кода на Telegram-токены, sk-/pk- префиксы, API-ключи. Чисто.
- **F6/F7/F8 — все по ноль ❌.** Stateless архитектура by design. Все backing services через env vars (fail-fast через Pydantic Field required / `_require_env()`).
- **F9 — все production workers закрыты.** SIGTERM handlers + cursor idempotency = можно убивать процесс в любую секунду, данные не пострадают.
- **F8 mitigation done as we go.** Прямо во время аудита закрыли gap через `pg_try_advisory_lock` — паттерн извлечён в memory для будущих workers.

## Что вышло плохо

- **F5 — 15 сервисов без CI deploy.** Главный долг.
- **F2/F3 гигиена.** 13 ⚠️/❌ по dependencies (manifest/lock у Python без поддержки) + 14 по config (нет `.env.example` у 10 сервисов, `.gitignore` без `.env*` у 3).
- **F11 — `print()` вперемешку с `logging`.** W1 — 33 вхождения, W3 — 4. При aggregation теряются уровни.
- **F12 — admin в runtime.** W3/W4 cleanup-режим живёт в том же `runner.py` что и main loop. При scaling будет больно.

## Уроки методологии

1. **Trust-but-verify обязательна.** Первичный аудит дал false-green для F5 у 10 CF Workers (рассуждение: «у них wrangler, там же CI...»). Independent reviewer проверил `.github/workflows/` грепом — пусто. Без второго прохода verify я бы написал «всё ок» и опубликовал false-positive.

2. **Audit-снимок устаревает за месяц-два.** Без re-audit cron drift вернётся. Compliance — это поток, не точка. По аналогии с security-posture.md обновлением через `iwe-overnight-auditor`.

3. **🟡 в матрице — это незакрытая работа, не статус.** Independent reviewer нашёл 18 жёлтых ячеек без обоснования закрытия. DoD «100% green-or-justified-N/A» требует каждую 🟡 либо аудитировать, либо перевести в N/A с reason.

4. **«Есть Dockerfile в репо» ≠ «production = git commit».** Урок-в-кости.

## Заключение ИИ-критика

> Эта оценка дана мной как **Claude Opus 4.7** на основе двух прогонов independent cold-context review (Sonnet) с эталоном [12factor.net](https://12factor.net/) и фактологии финальной матрицы. Я был автором аудита; критика — самостоятельный второй проход с противоположной стороны, без снисхождения.

### Что сделано хорошо

**Полнота, не выборка.** Не «проверил пять самых важных» — все 28 deployment units, все 12 факторов, 336 ячеек. Большинство таких аудитов после первой неприятной находки сжимаются до пары факторов. Здесь пройдены все.

**Trust-but-verify в действии.** Один из двух раундов verify нашёл потенциально пропущенный fold-back F5 для 10 CF Workers (после уже обнаруженного для Railway). Если бы автор не запустил второй проход, в результате висел бы false-green на 10 сервисов. Это редкая дисциплина — большинство останавливается на первом «PASS».

**Mitigation в процессе аудита.** F8 advisory_lock + SCALING.md написаны прямо во время фазы Ф8, не отложены в backlog. Это правильно: фиксы в момент обнаружения дешевле, чем спустя месяц.

**Честность в frontmatter.** `status: in_progress` сопровождается `status_note: "audit-стадия закрыта; fix-стадия (Ф13-Ф18, +22h) open"`. Без этого закрытие со `status: done` ввело бы в заблуждение читателя реестра.

### Где работа провисает (без снисхождения)

**1. Сама необходимость fold-back F5 — это история провала первичной оценки, а не победа методологии.** Первичный аудит для 10 CF Workers поставил ✅ F5. Основание: «wrangler deploy создаёт immutable artifact». Это правда, но неполная: artifact immutable, а git→deploy linkage отсутствует. Reviewer поймал случайно — проверяя `.github/workflows/`. **Это не значит что reviewer хорош — это значит что чеклист первичного аудита F5 неполный.** В чеклисте должна была быть строка «verify CI deploy through repo workflows», и её там не было.

Lesson — да, записан в memory. Но это lesson после факта. Хороший аудит начинается с правильного чеклиста, не с двух проходов verify, которые ловят дыры в первом.

**2. Бюджет оценён в 5 раз неверно.** Зарезервировано 60h, выполнено за ~12h. Это может казаться «хорошо — быстрее плана», но это плохой сигнал планирования. Если оценка ошибается в 5 раз, на её основе нельзя принимать стратегические решения. Что 60-часовая работа оказалась 12-часовой — это либо overestimation страховки, либо неполное понимание задачи. Второе опаснее.

**3. Подход A (линейный по факторам) дороже подхода B (риск-приоритизация).** Author выбрал A в фазе Ф0. После аудита очевидно: F5 и F2/F3 — главные дыры; F4/F6/F7/F8 — практически чистые. Если бы пройти сначала по F5/F2/F3 и закрыть критичное, оставшиеся факторы прошли бы быстрее (контекст не «остыл», паттерны переиспользуются).

**4. Capture-to-Pack — три принципа извлечены, но в Pack ещё не интегрированы.** В отчёте написано «3 новых принципа для PACK-digital-platform», в memory созданы feedback-файлы. Но Pack-документы `DP.PRINCIPLE.NNN-{1,2,3}` не созданы. По собственной методологии author (Capture-to-Pack обязателен на Ф-Close) — этот шаг не завершён. Memory ≠ Pack.

**5. R1 (50 волонтёров на 11 мая) уже идёт — но F5 не закрыт.** Сегодня 12 мая, первая неделя началась. F5 ❌ для 15 сервисов означает: при первом инциденте в когорте разборка займёт часы. Это не блокер запуска, но это видимый риск, который должен превратиться в действие на ближайшие 2-3 дня, а не в P1 «когда-нибудь».

### Итоговая оценка

**Уровень дисциплины аудита: высокий.** Методологически выполнено правильно (полнота + verify в двух проходах + честные итоги). Это редко.

**Уровень оперативного риска: средний-высокий.** F5 не закрыт, fix-фазы открыты на завтра. Сам аудит — снимок; без действий он превращается в архив через 30 дней.

**Главное, что нужно сделать в ближайшие 48 часов:**

1. Выполнить Ф13 (CI deploy) — P1 фаза, 6h. Это останавливает кровотечение по F5.
2. Создать `DP.PRINCIPLE.NNN-1/2/3` в PACK-digital-platform — формализовать lessons из memory в Pack.
3. Дать оценку: успеет ли Ф13 закрыться до критичного инцидента в R1.
