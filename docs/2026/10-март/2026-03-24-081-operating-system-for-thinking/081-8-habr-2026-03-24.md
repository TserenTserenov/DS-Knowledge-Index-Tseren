# Продуктивность ×2 — это не про инструменты. Это про культуру работы

У меня 36 активных рабочих продуктов. Архитектура платформы, телеграм-бот с пользователями, публикации, исследования. Параллельно — несколько окон Claude Code, каждое на своей задаче. Мультипликатор прошлой недели — 1.8x: за 6 физических часов результат на 11 часов.

Год назад я бы утонул. Сейчас — нет. Не потому что стал умнее. А потому что выстроил набор правил, которые работают автоматически — пока я работаю над содержанием.

Это не GTD, не Pomodoro и не «система продуктивности». Это ближе к операционной системе: набор правил, которые запускаются на входе в задачу и на выходе из неё, не дают потерять контекст и масштабируются от 25-минутной сессии до квартального планирования.

Ниже — 14 правил, каждое из которых появилось после конкретной ошибки. С кодом, конфигами и метриками.

<!--more-->

## 1. ОРЗ-фрактал: Открытие → Работа → Закрытие

Любая единица работы проходит три фазы. Фрактальность означает, что паттерн одинаков на трёх масштабах:

| Масштаб | Открытие | Работа | Закрытие |
|---------|----------|--------|----------|
| **Сессия** (25-90 мин) | Роль + метод + рабочий продукт | Выполнение + capture | Фиксация: что сделано, что узнал |
| **День** | План дня (календарь + РП) | Между Open и Close | Итоги + governance-синхронизация |
| **Неделя** | WeekPlan (бюджеты РП) | Между Open и Close | Ревью + мультипликатор |

**Ключевое:** Открытие — это не «сел и начал». Это осознанный выбор: кто я сейчас (роль), как буду действовать (метод), что должно получиться (рабочий продукт с критериями готовности).

**Почему это работает:** без закрытия знание остаётся в рабочей сессии и теряется. Я проверял: если не закрыть сессию — через день не помнишь, какое именно решение принял и почему. Закрытие — это `git commit` для мышления.

## 2. Каскад планирования: стратегия → день

```
Стратегия (год)
  └── Приоритеты месяца (3-5 результатов: R1, R2, R3...)
       └── План на неделю (РП с бюджетами в часах)
            └── План на день (РП + свободные блоки в календаре)
                 └── Сессия (один РП, одна роль)
```

Каждый уровень сужает фокус. Без этого каскада я ловил себя на том, что делаю «важное», но не то, что двигает к результату месяца.

**Priority Gate:** рабочий продукт ≥3 часов → обязательный вопрос: «К какому результату месяца (R1-R{N}) это ведёт?» Нет ответа → off-plan. Нужно решить: это важнее чего-то в плане, или это отвлечение?

## 3. Ритуал учёта: рабочий продукт + роль + метод

Две вещи, без которых работа превращается в суету: **что считать** и **кто делает**.

**Рабочий продукт — единица учёта:**

| Плохо (задача) | Хорошо (рабочий продукт) |
|---|---|
| «Написать документ» | «Спецификация Web App: 5 сценариев, модель данных, API endpoints» |
| «Разобраться с ботом» | «Асинхронный ДЗ-чекер v2: пакетная проверка + запись в цифровой двойник» |
| «Подумать про архитектуру» | «Архитектура Phase 2: спецификация + review с архитектором» |

Рабочий продукт имеет: номер (WP-172), бюджет (4 часа), приоритет, связь с результатом месяца.

**Роль и метод — контекст перед работой:**

```yaml
# Пример: Открытие сессии
role: Кодировщик (R6)
method: Реализация по спецификации
wp: WP-171 (ДЗ-чекер v2)
expected_output: MVP асинхронной проверки с записью в БД
```

Без явного выбора роли — скатываешься: начал как стратег, через 10 минут кодируешь. А бюджет времени утекает в незафиксированную работу.

## 4. Организация структуры знаний

Знание — не куча файлов. Это иерархия с уровнями доверия:

```
Производная документация (DS: код, конфиги, документация)
  ← База знаний предметной области (Pack: архитектура, модель домена, терминология)
    ← Принципы (SPF → FPF → ZP: фундамент, не зависит от проекта)
```

**Fallback Chain:** когда два источника противоречат — побеждает тот, кто выше в цепочке. «В документации бота написано одно, в архитектуре платформы — другое.» Иерархия даёт ответ без споров и без совещаний.

Без этой структуры знание расползается: одно и то же записано в трёх местах, версии конфликтуют. Организация знаний — это не про порядок, а про то, чтобы в любой момент знать, где искать правду.

## 5. ВДВ — три аспекта новой системы

Любая система — это процесс с входами и выходами:

| Аспект | Вопрос | Детали |
|--------|--------|--------|
| **В** — выполнение (процессы) | Как делать? | От кого получаем входные данные? На каком носителе (API, файл, чат)? Какой метод? Кому отдаём результат? |
| **Д** — данные | Что хранить? | Какие РП на каждом шаге? Какие системы хранят? Какие интерфейсы между системами? |
| **В** — видимость | Что увидит пользователь? | Экраны, отчёты, уведомления. Как человек взаимодействует? |

Обычно пропускают данные или не уточняют интерфейсы между системами. Чеклист: нарисуй входы и выходы (кто → что → кому), определи носители, перечисли РП на каждом шаге. Если не можешь — система не продумана.

## 6. Capture-to-Pack: автосохранение для знания

На каждом рубеже (подзадача завершена, паттерн обнаружен, решение принято) — проверка:

```
if (есть знание для записи):
    определить тип:
        доменное → Pack (база знаний предметной области)
        реализационное → DS docs/ (документация системы)
        правило для всех → CLAUDE.md (инструкции)
        крупный урок → memory/
    записать СРАЗУ
    анонсировать: "Capture: [что] → [куда]"
```

Без этого правила я принимал одни и те же решения 3-4 раза. Capture-to-Pack — `git commit` для знания. Не ты помнишь — система помнит.

## 7. АрхГейт: 7 характеристик для каждого решения

Перед архитектурным решением — обязательная оценка:

| Характеристика | Вопрос |
|----------------|--------|
| Эволюционируемость | Что сломается при изменении? |
| Масштабируемость | Что будет при 10x нагрузке? |
| Обучаемость | Сколько читать, чтобы начать? |
| Генеративность | Создаёт ли платформу для дальнейшего роста? |
| Скорость | Укладывается ли в бюджет времени отклика? |
| Современность | Не устарел ли подход? |
| Безопасность | Какие угрозы? |

Порог: ≥8 из 10 по каждой. Ниже — решение не предлагается.

## 8. Pre-action Gates: стоп-краны

```
Получил задание     → есть ли оно в плане?
Реализую сценарий   → описан ли use-case?
Добавляю инструмент → определён ли контур интеграции?
Делаю commit        → прочитал ли CLAUDE.md репозитория?
```

Каждый Gate — история одной ошибки. Когда-то потратил день на реализацию фичи, которой не было в плане. Теперь — автоматический стоп.

## 9. Осторожный мультитаскинг

Несколько окон ИИ параллельно, но с правилами:

- Каждая сессия = свой РП, своя роль. Не смешивать
- Мультипликатор = Σ бюджетов done-РП / физическое время (WakaTime)
- Цель: 1.5-2.5x
- >3 параллельных сессий → coordination overhead > parallelism gain

```
Пример дня:
  Физическое время:  6h (по WakaTime)
  Done-РП:           WP-170 (3h) + WP-73 фаза 1 (4h) + WP-167 пост (2h) + WP-139 (2h)
  Мультипликатор:    11h / 6h = 1.83x
```

## 10. Мультиагентность: альтернативная проверка

Результат одной модели проверяется другой. Причём не обязательно более сильной — даже слабая модель (Haiku) регулярно ловит ошибки, которые пропустила сильная (Opus).

Это работает по той же причине, по которой работает code review: автор слеп к собственным допущениям. Второй взгляд — даже менее опытный — видит то, что автор принял за очевидное.

Практика: после завершения РП — верификация отдельным агентом с context isolation (он не видит процесс создания, только результат и критерии).

## 11. Экзоскелетный режим

ИИ-система — экзоскелет, а не протез. Протез заменяет функцию (сними — не можешь). Экзоскелет усиливает (сними — можешь, но медленнее).

Опасность: если система думает за тебя — через полгода разучишься думать без неё. Три правила:

- **ИИ усиливает, человек решает.** Модель предлагает — я выбираю. Финальное решение всегда за мной.
- **Регулярные сессии без ИИ.** Раз в неделю — бумага, ручка, тишина. Чтобы мышление оставалось моим.
- **Навык первичен.** Если не могу объяснить решение без «ИИ подсказал» — это не моё решение.

Тест: если завтра все ИИ исчезнут — продолжу работать? Если да — экзоскелет. Если нет — протез.

## 12. Самоисправление

Заметил расхождение с реальностью → немедленно предлагаю конкретное исправление: файл, строка, что изменить. Одна ошибка не повторяется дважды.

Это правило зафиксировано в конфигурации ИИ-помощника — он тоже его знает и применяет.

## 13. Стоп-лист для рабочих продуктов

| Критерий | Сигнал | Действие |
|----------|--------|----------|
| Бюджет исчерпан | >150% без прогресса | СТОП. Переоценить |
| Блокер >2 недель | Внешняя зависимость не движется | Заморозить |
| Гипотеза опровергнута | Допущение оказалось неверным | Закрыть или переформулировать |
| Приоритет упал | Проблема больше не актуальна | В бэклог или закрыть |

Антипаттерн — sunk cost fallacy: «я уже столько вложил». Стоп-лист — решение на основе будущей ценности, не прошлых затрат.

## 14. Эволюция системы

Операционная система мышления — не монумент. Каждую неделю при закрытии — три вопроса: какое правило мешало? Какого не хватало? Какое обходил?

Правила, которые систематически обходятся — кандидаты на удаление. Правила, которые никогда не срабатывают — мёртвый вес. Лучше 10 живых правил, чем 30 формальных.

Эволюция — не «каждую неделю всё переписывать». Это точечные изменения после столкновений с реальностью. Правило появляется после боли. Уходит, когда перестаёт её предотвращать.

## Как это работает вместе

Правила не независимы. Они образуют операционную систему:

- **ОРЗ** — ядро (ритм: когда что делать)
- **Каскад** — планировщик (направление: зачем)
- **Ритуал учёта** — файловая система (единица: что считать и кто делает)
- **Структура знаний** — registry (где правда, иерархия доверия)
- **ВДВ** — проектировщик (входы, выходы, носители, интерфейсы)
- **Capture** — система хранения (знание: куда записать)
- **АрхГейт + Gates** — permissions (защита: от поспешных решений)
- **Мультитаскинг** — scheduler (параллелизм с ограничениями)
- **Мультиагентность** — CI/CD (альтернативная проверка качества)
- **Экзоскелет** — security policy (ИИ усиливает, не заменяет)
- **Самоисправление** — hot-fix pipeline (ошибка → немедленный фикс)
- **Эволюция** — release cycle (система меняется вместе с тобой)
- **Стоп-лист** — garbage collector (вовремя закрыть)

Убери ОРЗ — нет ритма, работа не начинается и не заканчивается осознанно. Убери Capture — знание не копится, одни и те же ошибки каждую неделю. Убери каскад — «делаю много, двигаюсь никуда». Убери экзоскелет — через полгода слабее, чем до системы.
