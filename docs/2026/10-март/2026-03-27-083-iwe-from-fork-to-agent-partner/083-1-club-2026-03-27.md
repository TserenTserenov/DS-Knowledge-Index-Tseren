# Развитие IWE: от форка к агенту-партнёру

Последние две недели я проектирую то, что определит следующие несколько лет IWE. Не фичу, не модуль — архитектуру того, как IWE существует в мире. Как человек получает его, как делает своим, как обновляет, и как IWE растёт вместе с ним.

Делюсь тем, что получается. Это не финальное решение — это snapshot мышления, которое продолжает развиваться.

## Ключевое различение: IWE — не платформа

Платформ будет как собак нерезаных. Вендоры AI раздавят любую софтверную платформу. Но методологию не раздавишь — она переживёт любую платформу.

IWE — это **операционная система интеллектуальной работы**. Как Ubuntu — не ядро Linux, а дистрибутив: ядро + пакеты + конфигурация + сообщество. IWE сажается поверх AI-платформ (Claude, Cursor, что угодно), а не конкурирует с ними.

Четыре компонента:

```
Ядро мышления      — чем думаешь (FPF → SPF → Pack → DS)
Культура работы    — как работаешь (протоколы, навыки, форматы)
Модель мастерства  — куда растёшь (Ученик → Просветитель)
Сообщество         — где живёшь (среда созидателей)
```

## Инструмент с зашитой теорией

IWE — не «ещё один инструмент продуктивности». Это инструмент, в котором **зашита теория**. Без понимания теории нельзя получить пользу — и даже небезопасно. Как хирургический инструмент: без обучения — опасен.

Поэтому программа личного развития — не маркетинг, а **часть продукта**. Персональное руководство создаётся конкретно под пользователя и доставляется прямо в его IWE.

Pack — обязательная часть IWE. Но пользователь должен создавать **свои** паки. Мы даём:
- Общую методологию и теорию (наши Pack)
- MCP к нашей базе знаний
- SPF как шаблон для пользовательских паков
- Seed-паки для старта

А пользователь создаёт:
- Свои Pack (предметные области, которыми он владеет)
- Свой MCP (его знания, его данные)

## Два слоя доставки

Одна из ключевых находок: нужны **два способа получить IWE**.

**Дистрибутив** (Git + Markdown + CLI) — для созидателей, которые хотят владеть своим окружением. Fork шаблона, setup.sh, полный контроль.

**Платформа-хостинг** (одна кнопка) — для новичков, которые ещё не готовы к Git. Заходишь на сайт, нажимаешь «Создать мой IWE», работаешь через веб-интерфейс. Вырастаешь → экспортируешь → владеешь.

Это не противоречие. Это Red Hat + Ubuntu: один дистрибутив, два способа получить. Платформа — managed-версия того же самого. Данные в Git + Markdown — экспорт = просто `git clone`.

## Три слоя архитектуры

```
┌──────────────────────────────────────────────────┐
│  Слой 3: Агент-партнёр                           │
│  • Знает методологию (IWE MCP)                   │
│  • Знает пользователя (его Pack, его MCP)        │
│  • Предлагает обновления, объясняет              │
│  • Создаёт персональную программу ЛР             │
│  • Учит теории в контексте практики              │
├──────────────────────────────────────────────────┤
│  Слой 2: Механика доставки                       │
│  • install (setup.sh → iwe-setup)                │
│  • update (update.sh → iwe-update, 3-way merge)  │
│  • extend (extensions/, params.yaml)             │
│  • migrate (detect + auto-fix)                   │
├──────────────────────────────────────────────────┤
│  Слой 1: Дистрибутив (файлы)                     │
│  • Ядро: CLAUDE.md, memory/, skills/, protocols  │
│  • Методология: FPF, SPF-шаблон, Base-паки       │
│  • Seed: Pack-шаблон, DS-шаблоны                 │
│  • Конфиг: .exocortex.env, params.yaml           │
└──────────────────────────────────────────────────┘
        ↕                           ↕
  Самостоятельная              Платформа-хостинг
  установка (Git+CLI)         (веб, одна кнопка)
```

**Слой 1** — это то, что пользователь получает. Файлы в Git, Markdown, YAML. Открытые форматы. Можно уйти в любой момент.

**Слой 2** — как пользователь устанавливает и обновляет. Сейчас bash-скрипты (fork + update.sh). Дальше — CLI, который растёт в руки агента.

**Слой 3** — целевой. Агент, который знает методологию и знает конкретного пользователя. Не просто «помощник», а партнёр по траектории от Ученика до Просветителя.

## Траектория: 1 → 2 → 3

Почему именно через 2, а не сразу в 3?

Агент без надёжной механики — как хирург без инструментов. Он знает что делать, но нечем. CLI (слой 2) — это руки агента. Агент (слой 3) — это голова.

Но CLI не становится отдельным продуктом — он **врастает в агента**.

## Шесть шагов: от багов до платформы

Вот как я вижу путь. Каждый шаг строится на предыдущем.

**Шаг 1. Стабилизация.** Прямо сейчас update.sh ломает IWE при обновлении — теряет настройки, не подставляет пути, не копирует skills. Шесть конкретных багов, которые нужно починить, прежде чем двигаться дальше. Это фундамент: если обновление ломает систему, всё остальное бессмысленно.

**Шаг 2. Кастомизация без страха.** Пользователь хочет добавить «рефлексию дня» в закрытие дня. Или отключить проверку видео в утреннем ритуале. Сейчас для этого нужно редактировать платформенные файлы — и при следующем обновлении всё слетает. Решение: директория `extensions/`, файл `params.yaml`, 3-way merge для CLAUDE.md. Кастомизируй сколько хочешь — обновления не трогают твоё.

**Шаг 3. Агент-обновитель.** Вместо «запусти bash update.sh и молись» — агент сам предлагает: «Вышла новая версия. Изменились протоколы Day Open и Day Close. У тебя есть расширение для Day Close — вот как его адаптировать к новой версии». Агент знает твой IWE, знает что изменилось, и объясняет на человеческом языке.

**Шаг 4. Персональная программа развития.** Агент проводит диагностику: где ты на траектории от Ученика до Просветителя? Какие практики освоены, какие — нет? Генерирует персональную программу и кладёт прямо в твой IWE. По мере продвижения — обновляет. Не «прочитай документацию», а «вот что тебе сейчас полезнее всего, исходя из того, где ты».

**Шаг 5. Платформа для новичков.** Не все готовы к Git и CLI. Для тех, кто хочет попробовать IWE — одна кнопка на сайте. Под капотом всё тот же дистрибутив, но управляемый через веб-интерфейс. Вырос, хочешь полный контроль — `git clone` и забирай всё с собой.

**Шаг 6. Экосистема расширений.** «Что я могу расширить?» — `/extend` покажет все точки. «Хочу установить чужое расширение» — формат пакетов. «Два расширения конфликтуют» — автоматическое разрешение. Это зрелость: не просто «можно кастомизировать», а «удобно кастомизировать».

Шаги 1-2 — фундамент (ближайшие недели). Шаги 3-4 — агент оживает (апрель-май). Шаги 5-6 — масштаб и зрелость (лето и дальше).

## Проблема множества MCP

У пользователя IWE три категории MCP:

| Категория | Кто даёт | Примеры |
|-----------|----------|---------|
| **IWE MCP** | Мы | knowledge-mcp (теория), guides-mcp, digital-twin-mcp |
| **Пользовательский MCP** | Пользователь | Его Pack-знания, его данные |
| **Внешние MCP** | Вендоры | Gmail, Calendar, Linear, Drive |

Проблемы: шум контекста (10+ MCP → Claude тратит токены на tool descriptions), конфликты имён, доставка, изоляция.

Принципы решения (гипотезы для валидации):
- **Namespace:** `iwe/search` vs `my/search` vs `ext/calendar`
- **Lazy activation:** не все MCP активны одновременно
- **Per-user isolation:** пользовательский MCP = его instance
- **Declarative config:** `.mcp.json` генерируется из конфигурации

Это отдельный архитектурный РП (WP-189), который связан с расширяемостью (WP-180) и Knowledge Gateway (WP-187).

## Модель расширяемости: 10 уровней

Что может кастомизировать пользователь IWE — от строки в файле до нового репозитория:

| Уровень | Что | Пример |
|---------|-----|--------|
| A | Добавить блок в файл | Рефлексия в Day Close |
| B | Создать файл | Свой скилл `/morning-health` |
| C | Создать директорию | Новая роль агента |
| D | Создать репозиторий | `DS-my-health` |
| E | Создать сценарий | Еженедельный ревью здоровья |
| F | Override параметра | Отключить video check |
| G | Discovery | «Что я могу расширить?» |
| H | Конфликты | Два расширения в одной точке |
| I | Миграция | Авто-фикс ссылок при обновлении |
| J | Sharing | Установить чужое расширение |

Паттерн: **drop-in** (как systemd) + **3-way merge** (как Copier) для CLAUDE.md + **overlay** для продвинутых. SOTA-исследование показало, что IWE опережает индустрию по формализации слоёв (L1/L2/L3), но отстаёт по developer experience кастомизаций.

## Принцип: человек свободен

Всё, что я описал выше, построено на одном принципе: **человек не должен зависеть от нас**.

- Данные в Git + Markdown → `git clone` = полный экспорт
- Методология в открытых файлах → смена AI-вендора не теряет знания
- Pack — его, не наш → забирает с собой
- Платформа-хостинг → вырос — забрал свой IWE и ушёл

Мы партнёр по траектории, не тюремщик. IWE помогает человеку расти от Ученика до Просветителя. Если он перерос нас — значит мы всё сделали правильно.
