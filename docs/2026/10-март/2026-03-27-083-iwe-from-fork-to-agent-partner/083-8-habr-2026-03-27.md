# Как я проектирую расширяемый дистрибутив для AI-окружения на 1000 пользователей

Я строю систему, которая организует интеллектуальную работу человека поверх AI: протоколы, базы знаний, skills, MCP-серверы, cron-агенты. Это не приложение — это экзокортекс для мышления: расширение человека, которое помнит и структурирует всё, что он узнал. Сейчас 100+ пользователей, и update pipeline ломается при каждом обновлении. В этой статье — как я проектирую архитектуру расширяемости, чтобы кастомизации пользователей не слетали при обновлении, а агент мог обновлять систему сам.

Технический стек: Git + Markdown + YAML + Claude Code (Claude CLI) + MCP-серверы + bash-скрипты + launchd. Всё в открытых форматах, без vendor lock-in.

## Проблема: fork-based доставка не масштабируется

Система доставляется как GitHub template repo. Пользователь делает fork, запускает `setup.sh`, получает рабочее окружение. Обновления — через `update.sh`, который тянет изменения из upstream.

Что ломается:

**1. Потеря конфигурации.** `setup.sh` спрашивает 7 параметров (имя, Telegram ID, пути) и подставляет их в файлы. `update.sh` перезаписывает эти файлы — и 5 из 7 параметров теряются. Hardcoded placeholder'ы возвращаются.

```bash
# Проблема: update.sh делает это
curl -s "$UPSTREAM_URL/$file" -o "$file"
# И перезаписывает персонализированные значения обратно на {{PLACEHOLDER}}
```

**2. Имя репо не подставляется.** `update.sh` скачивает файлы, в которых ссылки ведут на `FMT-exocortex-template` — имя шаблона, а не форка пользователя. Ни один путь не работает.

**3. Hardcoded пути в скриптах.** `strategist.sh:64` содержит абсолютный путь к `notify.sh`. На машине разработчика работает, у пользователя — `No such file or directory`.

**4. Нет skill propagation.** Claude Code skills живут в `.claude/skills/` шаблона. При setup они не копируются в workspace пользователя. При update — тоже. Пользователь не получает новые skills.

Четыре из шести багов — прямые симптомы одной проблемы: **нет персистентной конфигурации и единого механизма доставки**.

## Решение: .exocortex.env + 3-way merge + drop-in

### Слой 1. Персистентная конфигурация

Создаём `.exocortex.env` — единственный файл, который знает всё о конкретной установке:

```bash
# .exocortex.env — создаётся setup.sh, читается update.sh
EXOCORTEX_REPO="my-exocortex"
EXOCORTEX_OWNER="username"
WORKSPACE_DIR="/Users/username/IWE"
TELEGRAM_BOT_TOKEN="xxx"
TELEGRAM_CHAT_ID="123"
NOTIFY_PROXY=""
TIMEZONE="Europe/Moscow"
```

`setup.sh` создаёт этот файл. `update.sh` читает его и подставляет значения после скачивания upstream-файлов. `.exocortex.env` в `.gitignore` — никогда не перезаписывается.

Для существующих пользователей (у кого нет `.exocortex.env`) — detect-режим: `update.sh` извлекает значения из CLAUDE.md, plist-файлов и скриптов, генерирует `.exocortex.env`, просит проверить.

### Слой 2. Drop-in расширяемость

Паттерн взят из systemd: пользователь не редактирует платформенные файлы, а кладёт свои файлы рядом.

```
extensions/
├── protocol-close.after.md    # добавляется после платформенного блока
├── day-open.before.md         # добавляется перед
└── week-review.override.md   # полная замена блока
```

`update.sh` обновляет платформенные файлы, но **никогда не трогает `extensions/`**. Протоколы при выполнении читают оба источника:

```markdown
<!-- В protocol-close.md -->
... платформенный блок ...

<!-- AUTO: extensions/protocol-close.after.md -->
```

Для параметров — `params.yaml`:

```yaml
# params.yaml — пользовательские настройки
day_open:
  video_check: false      # отключить проверку видео
  news_section: true       # включить новости
close:
  reflection: true         # добавить рефлексию
```

Протоколы читают `params.yaml` и пропускают/добавляют блоки. Файл в `.gitignore` — обновления не трогают.

### Слой 3. 3-way merge для CLAUDE.md

CLAUDE.md — особый случай. Это и платформенный файл (мы обновляем ядро), и пользовательский (он добавляет свои правила в §8-§9). Перезапись невозможна, drop-in недостаточен.

Решение — 3-way merge (как в Copier):

```
upstream CLAUDE.md (старая версия)
          ↕ diff
upstream CLAUDE.md (новая версия)
          ↕ merge
user CLAUDE.md (с кастомизациями)
```

`update.sh` хранит хеш последней upstream-версии. При обновлении вычисляет diff между старой и новой upstream, применяет к пользовательскому файлу. Конфликты — показывает пользователю.

## Модель расширяемости: 10 уровней

Я формализовал что именно может кастомизировать пользователь — от строки в файле до нового репозитория:

| Уровень | Что | Механизм | Статус |
|---------|-----|----------|--------|
| A | Добавить блок в файл | `extensions/*.after.md` | Проектируется |
| B | Создать файл | Claude Code skills (`.claude/skills/`) | Работает |
| C | Создать директорию | Seed-шаблоны в `seed/` | Частично |
| D | Создать репозиторий | `seed/DS-template/` | Частично |
| E | Создать сценарий | launchd + Claude CLI | Работает |
| F | Override параметра | `params.yaml` | Проектируется |
| G | Discovery | `/extend` — каталог точек | Планируется |
| H | Конфликты | Приоритет: user > extension > platform | Планируется |
| I | Миграция | Авто-фикс ссылок при обновлении | Планируется |
| J | Sharing | Формат пакетов расширений | Планируется |

SOTA-исследование: systemd drop-in, Copier 3-way merge, Kustomize overlay, Claude Code skills/plugins, AGENTS.md, Obsidian plugins, n8n workflows.

Вывод: индустрия решает расширяемость per-tool (каждый инструмент по-своему). IWE нужен единый механизм поверх всего окружения — от конфигов до протоколов и MCP-серверов.

## Три слоя архитектуры

```
┌──────────────────────────────────────────────────┐
│  Слой 3: Агент                                   │
│  Вызывает update, объясняет изменения,           │
│  адаптирует обновления к кастомизациям            │
├──────────────────────────────────────────────────┤
│  Слой 2: Механика (CLI / scripts)                │
│  install · update · extend · migrate             │
│  .exocortex.env · 3-way merge · drop-in          │
├──────────────────────────────────────────────────┤
│  Слой 1: Дистрибутив (файлы)                     │
│  CLAUDE.md · memory/ · skills/ · protocols       │
│  .exocortex.env · params.yaml · extensions/      │
└──────────────────────────────────────────────────┘
```

**Слой 1** — файлы в Git. Открытые форматы. `git clone` = полный экспорт.

**Слой 2** — bash-скрипты сегодня, CLI завтра. Механика не видна пользователю — она работает под капотом.

**Слой 3** — агент, который использует слой 2 как инструменты. Вместо `bash update.sh` пользователь видит: «Вышла новая версия. Вот что изменилось. У тебя есть расширение для Day Close — вот как адаптировать».

Ключевой архитектурный принцип: **CLI врастает в агента**. Слой 2 не становится отдельным продуктом — он становится руками агента.

```
Сейчас:   bash update.sh (ручной запуск)
Шаг 1:    update.sh стабилен (.exocortex.env, skill propagation)
Шаг 2:    update.sh + extensions/ + params.yaml + 3-way merge
Шаг 3:    агент вызывает update + объясняет изменения
Шаг 4:    агент = основной интерфейс обновлений
```

## MCP: три категории, одна проблема

В системе три категории MCP-серверов:

| Категория | Источник | Примеры |
|-----------|----------|---------|
| **Платформенные** | Мы | knowledge-mcp (база знаний), guides-mcp, digital-twin-mcp |
| **Пользовательские** | Пользователь | Его базы знаний, его данные |
| **Внешние** | Вендоры | Gmail, Calendar, Linear, Drive |

Проблема: 10+ MCP-серверов в одном контексте. Claude тратит токены на tool descriptions, имена конфликтуют (два `search`), конфигурация `.mcp.json` захардкожена.

Гипотезы решения (не реализованы, проектируются):

**Namespace.** `iwe/search` vs `my/search` vs `ext/calendar`. Разделение на уровне имён tools.

**Lazy activation.** Не все MCP активны одновременно. Агент подключает нужный под задачу. Claude Code уже поддерживает это через MCP server selection.

**Per-user isolation.** Платформенный knowledge-mcp — shared service с auth. Пользовательский MCP — его instance. Данные изолированы.

**Declarative config.** `.mcp.json` генерируется из `.exocortex.env` при setup/update. Пользователь не редактирует JSON — он указывает какие MCP ему нужны в `params.yaml`.

## Два способа доставки

Для 100 пользователей fork + update.sh работает. Для 1000 — нет. Но и полностью менять модель рано.

Решение: **один дистрибутив, два способа получить**.

**Дистрибутив** (Git + CLI). Fork шаблона, `setup.sh`, полный контроль. Для тех, кто хочет владеть окружением. Обновления через `update.sh` (потом — через агента).

**Платформа-хостинг** (веб). Одна кнопка → под капотом тот же fork + setup, но автоматический. Пользователь работает через веб-интерфейс (чат с агентом). Вырос → `git clone` → забрал всё → ушёл на дистрибутив.

Аналогия: WordPress.org (скачай, поставь) vs WordPress.com (мы хостим). Red Hat vs Ubuntu. Один и тот же софт, разный delivery.

Архитектурное ограничение: `setup.sh` и `update.sh` должны быть **скриптуемыми** (без интерактивных промптов) — чтобы платформа могла вызывать их программно.

## Принцип: пользователь владеет данными

Все решения строятся на одном ограничении: **пользователь может уйти в любой момент**.

- Данные в Git + Markdown → `git clone` = полный экспорт
- Смена AI-вендора не теряет знания (методология в файлах, не в API)
- Платформа-хостинг → экспорт → полная автономия
- Забрать цифровой двойник — все данные о прогрессе, характеристиках, диагностике принадлежат пользователю
- Обнулить данные у нас — полное удаление, а не «деактивация аккаунта»
- Мы не можем «отключить» пользователю его систему — она на его компьютере

Это не маркетинговое обещание, а архитектурное ограничение, которое определяет каждое техническое решение: почему Git, а не проприетарная БД; почему Markdown, а не бинарный формат; почему fork, а не SaaS.
