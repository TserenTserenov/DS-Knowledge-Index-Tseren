# Среда, которая помнит тебя: архитектура расширяемости для AI-агентных систем

Я строю IWE — Intellectual Work Environment, среду интеллектуальной работы поверх Claude Code. Внутри — протоколы (открытие/закрытие дня, ритуалы сессий), шаблоны отчётов, чеклисты, конфигурации. Всё это описано в markdown и YAML, агент читает инструкции и выполняет их.

Система работает. Но вчера пользователь спросил: «Хочу при закрытии дня записывать детальную рефлексию — что получилось, что нет. Куда это добавить?»

Ответ «отредактируй protocol-close.md» — плохой. Потому что при следующем `update.sh` его правки затрутся. А ответ «форкни и веди сам» — ещё хуже: через месяц форк отстанет от платформы на 50 коммитов.

Это стандартная задача расширяемости шаблонных систем. Но для AI-агентных инструкций — нерешённая. Вот как я к ней подошёл.

## Три антипаттерна, которые я уже попробовал

**Inline editing.** Пользователь правит платформенный файл. Работает ровно до следующего обновления.

**Hardcoded zones.** `<!-- AUTHOR-ONLY -->...<!-- /AUTHOR-ONLY -->` — платформа явно размечает «пиши сюда». При sync скрипт заменяет содержимое на плейсхолдер `<!-- YOUR CUSTOM CHECKS HERE -->`. Проблема: каждая новая точка расширения — изменение платформы. Не масштабируется.

**Fork & forget.** Пользователь форкает шаблон целиком. Через месяц — дрейф. Через три — несовместимость. Через полгода — два разных продукта.

## Исследование: кто решал похожую задачу

Я исследовал 5 категорий систем. Вот что нашёл.

### systemd drop-in (Linux, с 2010)

Основной unit-файл — в `/usr/lib/systemd/system/`. Пользовательские дополнения — в `/etc/systemd/system/<unit>.d/*.conf`. Пакетный менеджер обновляет основной файл, drop-ins не затрагиваются.

Ключевое свойство: **база не знает о расширениях, расширения знают о базе**. Каждый drop-in — отдельный файл. Порядок — алфавитный.

Два типа параметров:
- **Заменяющие** (`ExecStart`) — последний побеждает
- **Аккумулирующие** (`OnCalendar`) — значения складываются

Для сброса: `ExecStart=` (пустое значение) перед новым.

### Copier 3-way merge (Python, SOTA для scaffold)

`copier update` помнит, от какой версии шаблона порождён проект. При обновлении:

1. Рендерит «чистый» проект из старой версии шаблона
2. Вычисляет diff между чистым и текущим пользовательским — это «пользовательский diff»
3. Рендерит новую версию шаблона
4. Применяет пользовательский diff поверх нового рендера через `patch`
5. Конфликты — inline markers (`<<<<<<< / ======= / >>>>>>>`)

Единственный инструмент, который честно решает «обновить шаблон, сохранить правки».

### Kustomize overlay (Kubernetes)

Base — read-only. Overlay — набор патчей:
- **Strategic merge patch** — YAML с теми же полями, указанные заменяются
- **JSON Patch (RFC 6902)** — хирургические `add/remove/replace/move`

Base обновляется, overlay применяются поверх. Нет явного конфликта — но возможна семантическая несовместимость.

### Claude Code skills/plugins (2025-2026)

Skills: `.claude/skills/name/SKILL.md` — автообнаружение, namespace. Но нельзя «расширить существующий скилл» — только создать новый.

Plugins (2025): `.claude-plugin/plugin.json` — manifest + skills + hooks. Namespace: `/plugin-name:skill-name`. Путь миграции: standalone → plugin.

### AGENTS.md (открытый стандарт, Linux Foundation, 2025)

Поддержан OpenAI, Google, GitHub, Cursor, Windsurf. Иерархия: `~/.codex/AGENTS.md` → `<repo>/AGENTS.md` → `<subdir>/AGENTS.md`. Proximity-based selection, нет merge.

### Что не решено нигде

Ни одна система не даёт:
1. Добавить блок в существующий платформенный файл без его редактирования
2. Обнаружить противоречие при обновлении платформы
3. Автоматически предложить исправление

## Модель расширяемости: 10 уровней

Из анализа я выделил 10 уровней кастомизации — от строки до экосистемы:

| Уровень | Операция | Пример | Паттерн |
|---------|----------|--------|---------|
| **A** | Добавить блок в файл | Рефлексия в Day Close | Drop-in |
| **B** | Создать файл | Свой скилл | Уже работает (skills) |
| **C** | Создать директорию | Новая роль агента | Convention-based |
| **D** | Создать репозиторий | Новая предметная область | Scaffold (seed/) |
| **E** | Создать сценарий | Еженедельный ритуал | Skill + config |
| **F** | Override параметра | Отключить шаг | Params overlay |
| **G** | Discovery | «Что можно расширить?» | Каталог extension points |
| **H** | Конфликты | Два расширения в одном месте | Priority + namespace |
| **I** | Миграция | Платформа переименовала шаг | Reference validation |
| **J** | Sharing | Отдать расширение другому | Package format |

## Архитектура решения

### Слои

```
L3 (платформа)     memory/protocol-close.md     ← update.sh обновляет
L4 (пользователь)  extensions/close.yaml         ← никогда не трогается
                   extensions/params.yaml        ← override параметров
```

### Extension points

Платформа определяет именованные точки — куда можно «повесить» расширение:

```yaml
# Определены в платформенном protocol-close.md
extension_points:
  - name: after:overview
    description: "После таблицы «что сделано»"
  - name: after:learnings
    description: "После «Что нового узнал»"
  - name: after:praise
    description: "После «Похвала»"
  - name: before:handoff
    description: "Перед «Задел на завтра»"
  - name: checklist:append
    description: "Добавить пункт в чеклист"
```

### Формат расширения

```yaml
# extensions/close.yaml (пользовательский файл)
name: "Рефлексия дня"
protocol: day_close
version: "1.0"

steps:
  - position: after:praise
    name: reflection
    type: interview          # агент задаёт вопросы
    optional: true           # можно пропустить
    questions:
      - "Что получилось?"
      - "Что не получилось и почему?"
      - "Что бы сделал иначе?"
    record_verbatim: true    # записывать дословно

templates:
  dayplan_results:
    position: results:append
    section: |
      ### Рефлексия дня
      **Что получилось:** {reflection.q1}
      **Что не получилось:** {reflection.q2}
      **Иначе:** {reflection.q3}

aggregate:
  on: week_close
  action: "Собрать рефлексии → паттерны → стратегирование"
```

### Runtime merge

При выполнении протокола:

```
1. Прочитать protocol-close.md (L3)
2. Прочитать extensions/*.yaml (L4)
3. Валидация: все position-ссылки резолвятся?
4. Merge: вставить расширения в указанные позиции
5. Выполнить объединённый протокол
```

### Обновление с обнаружением противоречий

При `update.sh`:

```
1. Загрузить новую версию базовых файлов
2. Для каждого extension-файла:
   a. Извлечь position-ссылки
   b. Проверить: шаг существует в новой базе?
   c. Нет → WARN с рекомендацией (ближайшее совпадение)
3. Показать предупреждения ДО применения
4. Обновить базу + записать версию-источник
```

Пример вывода:

```
update.sh v0.17.0 → v0.18.0

Обновлено:
  ✅ memory/protocol-close.md
  ⬜ extensions/close.yaml (не тронут)

Проверка совместимости:
  ⚠️ close.yaml: "after:praise" → переименован в "after:wins"
     Обновить ссылку? [да/нет]
```

## АрхГейт: оценка решения

Я оценил решение по 7 архитектурным характеристикам (ЭМОГССБ):

| Характеристика | Балл | Обоснование |
|----------------|------|-------------|
| Эволюционируемость | 9 | База и расширения эволюционируют независимо |
| Масштабируемость | 8 | Работает для 1 и N пользователей без координации |
| Обучаемость | 9 | YAML интуитивен, позиции читаемы |
| Генеративность | 9 | Произвольные расширения: шаги, секции, проверки |
| Скорость | 7 | YAML-парсинг при каждом выполнении — минимальный overhead |
| Современность | 8 | systemd (2010) + Copier (SOTA) + agent-native |
| Безопасность | 8 | User-space изолирован от platform-space |

**Средний: 58/70 (8.3).** Порог ≥56 пройден.

## Что дальше

Метод записан в Pack как DP.M.009 «Расширяемость шаблонных систем». Он не специфичен для IWE — применим к любой системе с шаблоном и инстансами.

Реализация идёт по фазам:
- **Ф1** (ближайшее): extensions/, extension points, пример рефлексии
- **Ф2**: discovery (каталог «что можно расширить»), конфликты между расширениями
- **Ф3**: авто-миграция ссылок при обновлении, sharing расширений между пользователями

Исходники метода и исследования — в открытом доступе в Pack-репозитории.
