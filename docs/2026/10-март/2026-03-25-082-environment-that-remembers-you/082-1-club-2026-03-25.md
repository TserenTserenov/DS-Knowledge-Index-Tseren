# Среда, которая помнит тебя: как сделать ИИ по-настоящему своим

Вчера один из пользователей написал: «При закрытии дня я выписываю вообще всё — что получилось, что нет и почему. Детально. Но не знаю, как это интегрировать в IWE и использовать на недельном стратегировании».

Простой запрос. Но за ним — архитектурный вопрос, который я откладывал: **как человек делает среду по-настоящему своей?**

Не «настраивает параметры». Не «выбирает тему оформления». А добавляет в систему то, чего в ней не было — свои ритуалы, свои вопросы, свои проверки. И при этом не теряет всё при следующем обновлении.

---

## Арендованная среда vs своя

Большинство инструментов — арендованные. Notion обновился — твои шаблоны поехали. ChatGPT поменял модель — твои Custom Instructions работают иначе. Obsidian обновил плагин — половина workflow сломалась.

Это не баг, это архитектура. Когда платформа и кастомизация живут в одном файле — обновление одного неизбежно ломает другое.

В IWE я столкнулся с тем же. Сейчас у нас три механизма кастомизации, и ни один не решает задачу целиком:

| Механизм | Что делает | Чего не может |
|----------|-----------|---------------|
| `AUTHOR-ONLY` блоки в протоколах | Защищает авторский контент от sync | Другой пользователь не знает как добавить свой блок |
| `USER-SPACE` в CLAUDE.md | Своя секция правил, не затирается при обновлении | Только один файл, не распространяется на протоколы |
| `day-rhythm-config.yaml` | Параметры (время помидора, видео-папки, новости) | Только параметры, нельзя добавить шаг в протокол |

Три механизма. Три разных формата. Ни один не отвечает на вопрос: «Хочу добавить рефлексию в закрытие дня — куда писать?»

---

## Как это решают другие системы

Я провёл исследование — от операционных систем до современных ИИ-агентов. Вот что нашёл.

**systemd (Linux, с 2010)** решил задачу элегантно: основной файл сервиса лежит в `/usr/lib/` (платформа), а пользовательские дополнения — в `.d/` директории рядом. Обновление пакета перезаписывает основной файл, но никогда не трогает `.d/`. Ключевой принцип: **база не знает о расширениях, расширения знают о базе**.

**Copier** (scaffold-менеджер, SOTA для шаблонных проектов) решает другую часть: при обновлении шаблона делает 3-way merge — сравнивает «старый шаблон → новый шаблон» и «старый шаблон → что пользователь изменил». Конфликты показывает явно, а не замалчивает.

**Claude Code** (с 2025) ввёл skills — `.claude/skills/name/SKILL.md` — каждый скилл в своём файле, автообнаружение, не конфликтует с платформой. Но нет механизма «расширить существующий скилл» — только создать новый.

**Ни одна система** не решает полную задачу: добавить своё в чужой протокол + обновлять платформу + обнаруживать противоречия.

---

## Что именно нужно

Когда человек говорит «хочу добавить своё», он может иметь в виду совсем разное. Самый частый случай — добавить блок в существующий протокол: «хочу три вопроса для рефлексии при закрытии дня». Это случай А, и именно он не работает. Создать новый скилл, новую роль агента, отдельный Pack для новой предметной области — это B-E, они частично работают через skills и seed-репозитории. Поделиться расширением с другим пользователем, пережить обновление без поломки кастомизаций — это уже зрелость системы.

Самое срочное — именно случай А: вставить своё в существующий протокол, не редактируя платформенный файл.

---

## Drop-in, не edit-in-place

Принцип простой: **пользователь создаёт свои файлы, никогда не редактирует платформенные**.

Платформа определяет именованные точки расширения — места, куда можно «повесить» своё:

```
Day Close:
  → after:overview     (после таблицы «что сделано»)
  → after:learnings    (после «Что нового узнал»)
  → after:praise       (после «Похвала»)
  → before:handoff     (перед «Задел на завтра»)
  → checklist:append   (добавить пункт в чеклист)
```

Пользователь создаёт файл `extensions/close.yaml`:

```yaml
name: "Рефлексия дня"
protocol: day_close

steps:
  - position: after:praise
    name: reflection
    type: interview
    optional: true
    questions:
      - "Что получилось?"
      - "Что не получилось и почему?"
      - "Что бы сделал иначе?"
    record_verbatim: true

aggregate:
  on: week_close
  action: "Собрать рефлексии → выявить паттерны → на стратегирование"
```

Что происходит:
1. При закрытии дня агент читает протокол (платформа) + extensions/ (пользовательское)
2. Вставляет рефлексию после «Похвала»
3. Записывает ответы дословно в DayPlan
4. При закрытии недели — агрегирует за 7 дней

При обновлении платформы:
```
update.sh v0.17.0 → v0.18.0

Обновлено:
  ✅ memory/protocol-close.md (платформа)
  ⬜ extensions/close.yaml (ваш файл — не тронут)

Проверка совместимости:
  ✅ extensions/close.yaml — все ссылки валидны
```

А если платформа переименовала шаг:
```
  ⚠️ extensions/close.yaml: "after:praise" → шаг переименован в "after:wins"
     Обновить ссылку? [да/нет]
```

## Переносимость — это про знания, а не про файлы

Переносимость данных — это когда ты можешь забрать файлы. Это уже работает: git, markdown, YAML, открытые форматы.

Но **переносимость среды** — это другое. Это когда ты забираешь не только файлы, а **свой способ работы**: свои ритуалы закрытия дня, свои вопросы для рефлексии, свои проверки, свои метрики. Всё, что делает среду *твоей*, а не стандартной.

Drop-in архитектура делает это возможным:
- Платформа обновляется → твоё не ломается
- Переезжаешь на новую машину → extensions/ переносится вместе с git
- Делишься с коллегой → он ставит твоё расширение, не трогая своё

Это как разница между «снимать квартиру» и «владеть домом, который можно достроить». В арендованной квартире нельзя снести стену. В своём доме — можно, и при этом фундамент (платформа) остаётся надёжным.

## Что сделано и что дальше

Сегодня я провёл архитектурную оценку (АрхГейт: 58/70) и записал метод в Pack — DP.M.009 «Расширяемость шаблонных систем». Три паттерна (drop-in, overlay, 3-way merge), критерии выбора, протокол обновления.

Дорожная карта:

| Фаза | Что | Когда |
|------|-----|-------|
| **Ф0** | Архитектура + метод в Pack | done (сегодня) |
| **Ф1** | extensions/, extension points, пример рефлексии | ближайшие недели |
| **Ф2** | Discovery («что можно расширить»), разрешение конфликтов | апрель |
| **Ф3** | Миграция при обновлении, sharing расширений | позже |

Самый интересный вопрос — уровень J (sharing). Когда один пользователь создал рефлексию дня, а другой может поставить её одной командой — это уже экосистема расширений. Но до этого нужно, чтобы уровни A-F работали надёжно.

Метод DP.M.009 — не специфичен для IWE. Любая система с шаблоном и инстансами (Copier-проекты, scaffold-фреймворки, agent instruction systems) может применить те же три паттерна. Мы просто первые, кто формализовал это для среды с ИИ-агентом.

Если вы уже используете IWE — расскажите, что бы вы добавили в свою среду, чего в шаблоне нет. Это поможет определить первые extension points.
