# Context Engineering для человека: как я построил среду, где ИИ-агент ошибается реже

Все обсуждают, что AI заберёт код, но оставит суждение (judgment). Тезис верный — но недостаточный. Модель может написать любой код. Инженер может оценить любой код. Но ни тот, ни другой не работают без контекста: какие принципы применимы, какие ограничения домена, какие решения уже приняты и почему.

Узкое место 2026 года — **Context Engineering**. Не prompt engineering, а инженерная дисциплина: **Write / Select / Compress / Isolate**. Каждая строка в контексте агента — архитектурное решение.

В этой статье я покажу, как устроена среда из 22 git-репозиториев, в которой Claude Code работает не с чистого листа, а в формализованном контексте: с доменными знаниями, протоколами и гейтами. С примерами конфигов и реальными фрагментами.

## Проблема: контекст теряется на каждой сессии

Типичный workflow с ИИ-ассистентом:

1. Открыл чат / сессию Claude Code
2. Объяснил, что делаешь, где остановился, какие ограничения
3. Поработал
4. Закрыл сессию
5. Завтра — с пункта 2 заново

Каждый раз — онбординг нового «сотрудника», который ничего не помнит. Решения теряются в чате. Знания остаются в голове. Ни одна модель не становится лучше от того, что вы ей вчера что-то объясняли.

## Решение: три слоя контекста

Я построил систему из трёх слоёв, каждый из которых решает свою задачу:

```
┌─────────────────────────────────────────────────┐
│  Слой 1: CLAUDE.md (~200 строк)                 │
│  Всегда в контексте. Триггеры + правила.        │
│  «Что делать ВСЕГДА»                            │
├─────────────────────────────────────────────────┤
│  Слой 2: memory/ (≤11 файлов, ≤150 строк каждый)│
│  Подгружается по триггеру из Слоя 1.            │
│  protocol-open.md, protocol-close.md, roles.md  │
│  «Что делать ПО ТРИГГЕРУ»                       │
├─────────────────────────────────────────────────┤
│  Слой 3: Pack-репозитории (DDD)                 │
│  Доменные знания: методы, различения, SOTA      │
│  PACK-digital-platform/, PACK-personal/         │
│  «Что ЗНАТЬ о предметной области»               │
└─────────────────────────────────────────────────┘
```

Это Context Engineering: **Write** (зафиксировать знание в нужном слое), **Select** (подгрузить только релевантное), **Compress** (бюджет на файл), **Isolate** (протокол подгружается только когда нужен, не всегда).

### Слой 1: CLAUDE.md — слим-ядро

`CLAUDE.md` лежит в корне рабочей директории. Claude Code читает его автоматически при старте каждой сессии. Это — единственный файл, который **всегда** в контексте.

Принцип: минимум содержания, максимум триггеров. Не «расскажи модели всё», а «расскажи модели, где искать».

Реальный фрагмент:

```markdown
## 2. ОРЗ-фрактал (Открытие → Работа → Закрытие)

| Масштаб   | Стадия    | Протокол                    | Триггер                      |
|-----------|-----------|-----------------------------|-----------------------------|
| Сессия    | Открытие  | protocol-open.md § Сессия   | Любое задание               |
| Сессия    | Работа    | protocol-work.md § Сессия   | После прохождения Открытия  |
| Сессия    | Закрытие  | protocol-close.md § Сессия  | «закрываю» / «всё»         |
| День      | Открытие  | protocol-open.md § День     | «открывай день»             |
| День      | Закрытие  | protocol-close.md § День    | «закрываю день»             |
```

Агент видит таблицу. Когда я говорю «закрываю» — он загружает `protocol-close.md` и выполняет алгоритм. Протокол не тратит контекстное окно, пока не понадобился.

### Слой 2: memory/ — протоколы по запросу

Директория `memory/` содержит файлы, которые подгружаются по триггерам из CLAUDE.md. Жёсткий бюджет: ≤11 файлов, каждый ≤150 строк.

Пример — `protocol-close.md`, алгоритм закрытия сессии:

```markdown
### Алгоритм Quick Close (6 шагов)

0. Pull → git pull --rebase
1. Commit + Push — все изменения зафиксированы
2. KE (Knowledge Extraction) — собрать отложенные captures:
   - Собрать captures → классифицировать → маршрутизировать
   - Доменное → Pack, реализационное → DS, операционное → memory
3. Verification Gate — проверить критерии готовности РП
4. MEMORY.md — обновить статус рабочего продукта
5. Отчёт — 4-6 строк: что сделано, что осталось, captures
```

Без этого протокола каждая сессия заканчивалась бы потерей: знание остаётся в чате и умирает вместе с контекстным окном.

### Слой 3: Pack — доменные знания по DDD

Pack — это git-репозиторий, который хранит формализованные знания предметной области. По сути — Bounded Context из DDD, но для знаний, а не для микросервисов.

```
PACK-digital-platform/
├── 01-core/          # Концепции, различения, глоссарий
├── 02-domain-entities/ # Роли, агенты, сервисы
├── 05-failure-modes/  # Что может пойти не так
├── 06-sota/          # Референсные подходы
├── 07-map/           # Каталог сервисов
└── 08-use-cases/     # Пользовательские сценарии
```

Когда агент работает с задачей в домене «цифровая платформа», он обращается к Pack за доменными знаниями — не к своему обучению, а к **моим** формализованным знаниям. Модель знает Computer Science. Pack знает **мой** домен.

Иерархия приоритетов (fallback chain):

```
DS (реализация, 3-й) → Pack (домен, 2-й) → Base (принципы: SPF → FPF → ZP)
```

Конфликт между реализацией и доменом? Побеждает Pack. Конфликт между доменом и принципами? Побеждает принцип.

## Capture-to-Pack: знание не теряется в чате

Главная проблема с «суждение останется за людьми» — оно живёт в голове и теряется. Решение: на каждом рубеже работы (подзадача завершена, решение принято, паттерн обнаружен) агент проверяет таблицу маршрутизации:

```markdown
| Тип знания                         | Куда                  | Когда  |
|------------------------------------|----------------------|--------|
| Правило для всех репо (1-3 строки)  | ~/IWE/CLAUDE.md      | Сразу  |
| Правило для одного репо             | <repo>/CLAUDE.md     | Сразу  |
| Доменное (архитектура, паттерны)    | Соответствующий Pack  | Close  |
| Реализационное (вендор, стек)       | DS docs/             | Close  |
| Крупный урок                        | memory/<topic>.md    | Close  |
```

На Close агент запускает Knowledge Extraction: собирает отложенные captures, классифицирует и записывает в нужное место. Знание не умирает вместе с сессией — оно формализуется и доступно в следующей сессии, завтра и через месяц.

## АрхГейт: формализация инженерного вкуса

«Вкус эксперта не коммодитизируется» — но его можно операционализировать. В CLAUDE.md прописан гейт: каждое архитектурное решение проходит оценку по 7 характеристикам.

```markdown
## АрхГейт — ОБЯЗАТЕЛЬНАЯ оценка

| Характеристика      | Вопрос                                  |
|---------------------|----------------------------------------|
| Эволюционируемость  | Что сломается при изменении?           |
| Масштабируемость    | Что будет при 10x?                     |
| Обучаемость         | Сколько читать, чтобы начать?          |
| Генеративность      | Создаёт платформу для будущих решений? |
| Скорость            | Бот <3 сек, CLI <1 сек?               |
| Современность       | Соответствует SOTA?                    |
| Безопасность        | PII, секреты, injection surface?       |

Порог ≥8. Ниже — не предлагать.
```

Агент не может предложить архитектурное решение, не заполнив таблицу. Это не заменяет суждение — это его усилитель. Экзоскелет, не протез.

## Trade-offs

Система не бесплатная. Вот с чем приходится жить:

**Стоимость поддержки.** 22 репозитория, протоколы, Pack — всё это нужно актуализировать. Устаревший Pack хуже, чем никакого: модель примет устаревшее знание за текущее.

**Бюджет контекста.** CLAUDE.md + memory/ + Pack — всё это ест контекстное окно. Отсюда жёсткие лимиты: ≤200 строк на CLAUDE.md, ≤11 файлов в memory/, ≤150 строк на протокол. Без бюджета — bloat.

**Порог входа.** Человеку без опыта DDD и системного мышления эта архитектура покажется overengineering. И для задач уровня «напиши функцию» она действительно избыточна. Окупается на горизонте месяцев, когда контекст накапливается.

**Single point of knowledge.** Pack — source-of-truth. Если знание не в Pack, его для агента не существует. Это и сила (один источник правды), и слабость (забыл записать — агент не знает).

## Что в итоге

Общий нарратив: «инженер + AI-инструмент». На практике: **инженер + среда знаний + протоколы + гейты**.

AI пишет код — человек проектирует контекст, в котором AI работает. Суждение формализовано в протоколах и гейтах. Знание не теряется — маршрутизируется по типу. Архитектурные решения проходят через оценку. Каждая сессия начинается не с чистого листа, а с накопленного контекста.

Код — commodity. Суждение — необходимо, но недостаточно. Настоящий рычаг — как ты организуешь знания, контекст и обратную связь для себя и своих агентов.

Context engineering с системным мышлением — новый syntax. И он пока не коммодитизирован.
