# Context Engineering на практике: CLAUDE.md, протоколы и доменные знания в git

Каждая новая сессия с ИИ-ассистентом — это онбординг сотрудника, который ничего не помнит. Вы объясняете контекст, ограничения, решения — а завтра всё сначала. Prompt engineering здесь не поможет: проблема не в качестве промпта, а в отсутствии **инженерии контекста**.

В этой статье — конкретная архитектура из трёх слоёв, которую можно воспроизвести за вечер. С реальными конфигами, кодом и объяснением, почему каждый слой устроен именно так.

## Что такое Context Engineering

Термин ввёл Андрей Карпатый, противопоставив его prompt engineering. Если prompt engineering — это «как сформулировать запрос», то context engineering — это «как спроектировать всю информационную среду, в которой работает модель».

Четыре операции:

| Операция | Что делает | Пример |
|----------|-----------|--------|
| **Write** | Зафиксировать знание в нужном месте | Записать архитектурное решение в файл, а не оставить в чате |
| **Select** | Подгрузить только релевантное | Протокол код-ревью загружается при ревью, а не всегда |
| **Compress** | Уложиться в бюджет контекста | Файл ≤150 строк, иначе — разбить |
| **Isolate** | Разделить контексты | Доменные знания отдельно от реализации |

## Архитектура: три слоя

```
┌───────────────────────────────────────────────┐
│  Слой 1: CLAUDE.md (~200 строк)               │
│  Загружается автоматически. Триггеры + правила│
├───────────────────────────────────────────────┤
│  Слой 2: memory/ (≤11 файлов × ≤150 строк)   │
│  Загружается по триггеру из Слоя 1            │
├───────────────────────────────────────────────┤
│  Слой 3: Доменные репозитории                 │
│  Загружаются по запросу агента                │
└───────────────────────────────────────────────┘
```

Разберём каждый слой с кодом.

### Слой 1: CLAUDE.md — точка входа

`CLAUDE.md` — файл в корне проекта, который Claude Code читает автоматически при старте сессии. Это единственный файл, который **всегда** в контексте.

Принцип: минимум содержания, максимум указателей. Не «расскажи модели всё», а «расскажи модели, где искать».

```markdown
# CLAUDE.md

## Блокирующие правила

1. **При ЛЮБОМ задании** → прочитай `memory/protocol-open.md` → выполни ДО начала работы.
2. **При «закрываю»** → прочитай `memory/protocol-close.md` → выполни.
3. **Перед архитектурным решением** → оценка по 7 характеристикам. Порог ≥8/10.

## Маршрутизация знаний (Capture-to-Pack)

| Тип знания | Куда записать | Когда |
|------------|--------------|-------|
| Правило для всех проектов | CLAUDE.md | Сразу |
| Правило для одного проекта | <project>/CLAUDE.md | Сразу |
| Доменное знание | domain-knowledge/ | При закрытии сессии |
| Реализационное решение | docs/ | При закрытии сессии |

## Ссылки на протоколы

| Ситуация | Файл |
|----------|------|
| Начало работы | memory/protocol-open.md |
| Закрытие сессии | memory/protocol-close.md |
| Терминология | memory/glossary.md |
| Архитектурные решения | memory/arch-decisions.md |
```

**Что здесь происходит.** Агент получает задание — первым делом читает `protocol-open.md`. Не потому что «так настроено», а потому что правило стоит первым и помечено как блокирующее. Протокол проверяет: есть ли задача в плане? К какому результату она ведёт? Только после этого — работа.

Это ~50 строк. Остальные 150 — на специфику проекта: fallback chain для приоритетов, pre-commit проверки, ссылки на доменные репо.

### Слой 2: memory/ — протоколы по запросу

Директория `memory/` содержит файлы, которые загружаются **только по триггеру** из CLAUDE.md. Агент не тратит контекстное окно на протокол закрытия, пока не услышит «закрываю».

Пример — `protocol-close.md`:

```markdown
# Протокол закрытия сессии

## Алгоритм (6 шагов)

1. `git pull --rebase` — синхронизация
2. `git add` + `git commit` + `git push` — зафиксировать изменения
3. Knowledge Extraction — собрать знания из сессии:
   - Что узнали нового? → записать в domain-knowledge/
   - Какое решение приняли? → записать в docs/decisions/
   - Какую ошибку нашли? → записать в memory/lessons.md
4. Обновить статус задачи в плане
5. Обновить memory/status.md — текущее состояние проекта
6. Отчёт: что сделано, что осталось, что записано
```

**Зачем это нужно.** Без протокола закрытия каждая сессия заканчивается потерей. Знание остаётся в чате и умирает вместе с контекстным окном. С протоколом — агент сам маршрутизирует знания по типу: доменное → в одно место, реализационное → в другое, урок → в третье.

Другой пример — `protocol-open.md`:

```markdown
# Протокол открытия сессии

1. Прочитать memory/status.md — где остановились?
2. Прочитать plan.md — какие задачи на сегодня?
3. Проверить: задание пользователя совпадает с задачей в плане?
   - Да → работаем
   - Нет → СТОП: «Такой задачи нет в плане. Создать?»
4. Определить, какие файлы затронуты → прочитать их
```

Это решает проблему «каждый раз объяснять контекст». Агент сам поднимает контекст из файлов при старте.

**Бюджет.** Жёсткое ограничение: ≤11 файлов в `memory/`, каждый ≤150 строк. Превысил — разбивай или сжимай. Без бюджета `memory/` раздувается и сжирает контекстное окно.

### Слой 3: доменные знания в отдельных репозиториях

Третий слой — git-репозитории с формализованными знаниями предметной области. По аналогии с Bounded Context из DDD, но для знаний, а не для микросервисов.

```
domain-knowledge/
├── 01-core/              # Ключевые концепции и глоссарий
│   ├── glossary.md       # Ubiquitous Language проекта
│   └── distinctions.md   # Явные различения (X ≠ Y)
├── 02-architecture/      # Архитектурные решения
│   ├── principles.md     # Принципы (не более 15)
│   └── decisions/        # ADR (Architecture Decision Records)
├── 03-failure-modes/     # Что может пойти не так
│   └── known-issues.md
└── 04-sota/              # Референсные подходы
    └── references.md
```

**Зачем отдельный репозиторий.** Доменные знания живут дольше реализации. Вы можете переписать бэкенд с Python на Go, но бизнес-правила останутся теми же. Если они в коде — потеряются при переписывании. Если в отдельном репо — переживут любой рефакторинг.

Пример записи в `distinctions.md`:

```markdown
## Процесс ≠ Сервис

**Процесс** — описание метода (рецепт, SOP): последовательность шагов для достижения результата.

**Сервис** — именованная точка входа: API endpoint, CLI-команда, бот-команда.

Процесс может быть реализован несколькими сервисами. Сервис может участвовать в нескольких процессах.

**Почему важно:** если путать, то при изменении API ломаются описания процессов, и наоборот.
```

Когда агент работает с задачей, он обращается к доменному репо за терминологией и ограничениями — не к своему обучению, а к **вашим** формализованным знаниям.

**Иерархия приоритетов (fallback chain):**

```
Реализация (код, docs/) → Домен (domain-knowledge/) → Принципы (CLAUDE.md)
```

Конфликт между реализацией и доменом? Побеждает домен. Конфликт между доменом и принципами? Побеждает принцип.

## Формализация инженерного суждения: гейты

Можно пойти дальше протоколов и формализовать критерии принятия решений. Пример — архитектурный гейт:

```markdown
## Архитектурный гейт (в CLAUDE.md)

Перед предложением архитектурного решения — оценить по 7 характеристикам:

| Характеристика     | Вопрос                                    | Оценка |
|--------------------|------------------------------------------|--------|
| Эволюционируемость | Что сломается при изменении?             | ?/10   |
| Масштабируемость   | Что будет при 10x нагрузки?              | ?/10   |
| Обучаемость        | Сколько читать новичку, чтобы начать?    | ?/10   |
| Генеративность     | Создаёт платформу для будущих решений?   | ?/10   |
| Скорость           | Укладывается в SLA?                      | ?/10   |
| Современность      | Соответствует текущему SOTA?             | ?/10   |
| Безопасность       | PII, секреты, injection surface?         | ?/10   |

Средний балл < 8 → не предлагать. Переработать.
```

Агент не может предложить архитектурное решение, не заполнив таблицу. Это не замена суждения — это его усилитель. Экзоскелет, не протез: вы всё равно принимаете решение, но с явными критериями.

## Как это выглядит в работе

Типичная сессия:

```
Я: «добавь rate limiting в API»

Агент (читает protocol-open.md):
→ Читает memory/status.md — поднимает контекст
→ Проверяет план — задача есть? Да, задача #42
→ Читает domain-knowledge/02-architecture/principles.md
→ Видит принцип: «SLA: API < 200ms p99»
→ Заполняет архитектурный гейт для решения с Redis
→ Средний балл 8.4 → предлагает решение

Я: «закрываю»

Агент (читает protocol-close.md):
→ Коммитит и пушит
→ Knowledge Extraction:
  - «Решение: Redis для rate limiting» → docs/decisions/
  - «rate limit = 100 req/min per user» → domain-knowledge/
→ Обновляет статус задачи #42 → done
→ Отчёт: «Добавлен rate limiting (Redis, 100 req/min).
   Записано: ADR в docs/, лимит в domain-knowledge/»
```

Без этой архитектуры: завтра я открою новую сессию и буду заново объяснять, что мы используем Redis, какой лимит выбрали и почему. С ней — агент поднимет контекст из файлов за секунды.

## Как начать: минимальный набор за 30 минут

Не нужны 22 репозитория. Начните с трёх файлов:

**1. `CLAUDE.md` в корне проекта (10 минут)**

```markdown
# Инструкции для Claude Code

## Правила
1. При начале работы — прочитай memory/status.md
2. При «закрываю» — обнови memory/status.md
3. Новое знание о домене — запиши в domain-knowledge/

## Терминология проекта
- [ваши термины и их значения]
```

**2. `memory/status.md` (5 минут)**

```markdown
# Текущее состояние

## Последняя сессия: [дата]
- Что сделано: ...
- Что осталось: ...
- Открытые вопросы: ...

## Активные задачи
- [ ] Задача 1
- [ ] Задача 2
```

**3. `domain-knowledge/glossary.md` (15 минут)**

```markdown
# Глоссарий проекта

## Термины
| Термин | Определение | Не путать с |
|--------|------------|-------------|
| Пользователь | Зарегистрированный аккаунт с подтверждённым email | Посетитель (без регистрации) |
| Подписка | Активный платный план | Триал (бесплатный период) |
```

Этого достаточно, чтобы агент перестал начинать каждую сессию с чистого листа. Дальше — наращивайте по мере необходимости: протоколы, гейты, отдельный репозиторий для доменных знаний.

## Ограничения и trade-offs

**Стоимость поддержки.** Файлы нужно актуализировать. Устаревшее доменное знание хуже, чем никакого: модель примет устаревшее за текущее. Решение — протокол закрытия сессии, который принуждает к актуализации.

**Бюджет контекста.** Всё, что загружается, ест контекстное окно. Отсюда жёсткие лимиты: ≤200 строк CLAUDE.md, ≤11 файлов в memory/. Без бюджета — bloat, и модель начинает терять важное в шуме.

**Порог входа.** Для проекта на один вечер эта архитектура избыточна. Окупается на горизонте недель, когда контекст начинает накапливаться и переиспользоваться между сессиями.

**Single point of knowledge.** Доменное знание в файлах — единственный источник правды для агента. Забыли записать — агент не знает. Это и сила (один источник), и дисциплина (нужно записывать).

## Итого

Context engineering — это не prompt engineering с модным названием. Это инженерная дисциплина: спроектировать, какую информацию модель получает, когда, в каком объёме и с каким приоритетом.

Минимальный набор: `CLAUDE.md` + `memory/status.md` + глоссарий. Три файла, 30 минут, и агент начинает работать с вашим контекстом, а не с чистого листа.
