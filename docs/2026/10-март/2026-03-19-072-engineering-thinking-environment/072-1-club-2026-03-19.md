# Инженерия среды мышления: context engineering для человека, а не только для кода

Говорят: «AI заберёт код, но не заберёт суждение (judgment)». Мол, вкус и системное мышление — вот что останется за человеком.

Это было правдой в 2025 году. Но нужно идти дальше.

Модель может написать любой код. Хороший инженер может оценить любой код. Но ни модель, ни инженер не могут работать без контекста: какие принципы применимы, какие ограничения домена, какие решения уже приняты и почему.

Узкое место сейчас — **Context Engineering**. Не prompt engineering, а инженерная дисциплина: Write / Select / Compress / Isolate. Каждая строка в контексте агента — архитектурное решение. И этот навык вкупе с системным мышлением пока не коммодитизирован.

---

## Как это выглядит на практике

У меня работает IWE (Intellectual Work Environment) — рабочая среда из 22 репозиториев, в которой ИИ-агенты не просто пишут код, а работают в среде знаний.

### Три слоя контекста

```
┌─────────────────────────────────────────────────┐
│  CLAUDE.md (~200 строк)                         │
│  Триггеры, правила, fallback chain              │
│  «Что делать ВСЕГДА»                            │
├─────────────────────────────────────────────────┤
│  memory/ (≤11 файлов, протоколы ≤150 строк)     │
│  protocol-open.md, protocol-work.md,            │
│  protocol-close.md, navigation.md, roles.md     │
│  «Что делать ПО ТРИГГЕРУ»                       │
├─────────────────────────────────────────────────┤
│  Pack (доменные знания, DDD)                    │
│  PACK-digital-platform/, PACK-personal/         │
│  Методы, различения, SOTA, failure modes        │
│  «Что ЗНАТЬ о предметной области»               │
└─────────────────────────────────────────────────┘
```

**CLAUDE.md** — слим-ядро. Всегда в контексте. Содержит триггеры, которые подгружают протоколы из memory/ только когда нужно. Это — Context Engineering в чистом виде: не «дай модели всё», а «дай модели нужное в нужный момент».

### Протокол ОРЗ: три стадии каждой сессии

Каждая рабочая сессия проходит три стадии — Открытие, Работа, Закрытие:

```
Открытие                    Работа                     Закрытие
─────────────────────────────────────────────────────────────────
WP Gate: есть РП?     →    Capture-to-Pack            →  KE (Knowledge Extraction)
Какие сервисы?        →    «Есть ли знание?»          →  Commit + Push
Подход согласован?    →    Verify на рубеже            →  MEMORY.md обновлён
```

Пропуск Открытия = незапланированная работа. Пропуск Закрытия = потерянное знание.

Вот реальный фрагмент из моего CLAUDE.md — таблица маршрутизации знаний, которую агент проверяет на каждом рубеже:

```markdown
| Тип знания                        | Куда                    | Когда  |
|-----------------------------------|-------------------------|--------|
| Правило для всех репо (1-3 строки) | ~/IWE/CLAUDE.md         | Сразу  |
| Правило для одного репо            | <repo>/CLAUDE.md        | Сразу  |
| Доменное (архитектура, паттерны)   | Соответствующий Pack    | Close  |
| Реализационное (вендор, стек)      | DS docs/                | Close  |
| Крупный урок                       | memory/<topic>.md       | Close  |
```

Агент на каждом рубеже спрашивает: «есть ли знание для записи?» Знание маршрутизируется по типу: доменное → Pack, реализационное → DS, операционное → memory. Суждение растёт не от написания кода, а от осознанной фиксации решений и их оснований.

### АрхГейт: операционализация вкуса

«Вкус эксперта не коммодитизируется» — верно, но его можно операционализировать.

Каждое архитектурное решение в моей среде проходит оценку по 7 характеристикам:

| Характеристика      | Вопрос                                             |
|---------------------|----------------------------------------------------|
| Эволюционируемость  | Что сломается при изменении?                       |
| Масштабируемость    | Что будет при 10x?                                 |
| Обучаемость         | Сколько читать, чтобы начать?                      |
| Генеративность      | Создаёт платформу для будущих решений?              |
| Скорость            | Бот <3 сек, CLI <1 сек?                            |
| Современность       | Соответствует SOTA?                                |
| Безопасность        | PII, секреты, injection surface?                   |

Порог — 8 из 10. Ниже — не предлагать. Это не замена вкуса — это его усилитель. Экзоскелет, не протез.

### Fallback Chain: иерархия приоритетов

Когда агент принимает решение, он проверяет цепочку приоритетов:

```
DS (реализация) → Pack (домен) → Base (принципы: SPF → FPF → ZP)
```

Это DDD в чистом виде: Bounded Context, Ubiquitous Language, Context Map — но не для микросервисов, а для организации знаний человека. Pack — единственный source-of-truth для доменного знания. DS меняется вслед за Pack, не наоборот.

## Почему это работает

Общий нарратив — «инженер + AI-инструмент». На практике получается иначе: **инженер + среда знаний + агенты + протоколы**.

AI пишет код — а человек с системным мышлением проектирует контекст, в котором AI работает. Суждение не в голове инженера — оно формализовано в протоколах и гейтах. Вкус не просто «не коммодитизируется» — он операционализируется.

Будущее инженерии — не «суждение вместо кода». Это инженерия самой среды мышления. Код — commodity. Суждение — необходимо, но недостаточно. Настоящий рычаг — как ты организуешь знания, контекст и обратную связь для себя и своих агентов.

Context engineering с системным мышлением — это новый syntax. И он пока не коммодитизирован.
