# Как SOTA-практики заполняют структуру Pack: маппинг для авторов

SPF задаёт **слоты** — что должно быть в Pack. Но как наполнить каждый слот современными методами? Для этого существует маппинг SPF ↔ SOTA.

Этот пост — для тех, кто создаёт Pack или проектирует AI-системы на основе знания.

## Четыре уровня и их роли

| Уровень | Что | Роль |
|---------|-----|------|
| FPF | Метапринципы корректного мышления | Первые принципы |
| SPF | Спецификация ядра предметной области | Форма и процесс |
| SOTA | Лучшие методы из индустрии | Заполнители слотов SPF |
| DDD | Метод добычи и инженерной реализации | Операционализация |

> SPF определяет СЛОТЫ. SOTA заполняет слоты МЕТОДАМИ.

## Ключевые маппинги

### Структура Pack → SOTA

| Слот Pack | SOTA-практика | Что даёт |
|-----------|---------------|----------|
| Bounded Context | DDD Strategic (DP.SOTA.001) | Context Mapping, контракты между контекстами |
| Словарь | Ubiquitous Language | Единый язык в коде, UI, документах |
| Различения | DSL→DSLM (DP.SOTA.010) | Машинно-проверяемые доменные правила |
| Связи между элементами | Coupling Model (DP.SOTA.011) | 3 измерения: knowledge/distance/volatility |
| Многовидовые представления | Multi-Representation Arch (DP.SOTA.012) | Один Pack → множество view |

### Загрузка Pack в ИИ-агента → 3 слоя

Самое практичное: как Pack загружается в контекст агента.

| Слой | Файлы | Когда загружать |
|------|-------|-----------------|
| **Layer 0** (всегда, ≤2K токенов) | `00-pack-manifest.md`, `01A-bounded-context.md` | При любом обращении |
| **Layer 1** (по навигации, ≤5K) | `07-map/`, `01B-distinctions.md`, индексы | Нужен обзор связей |
| **Layer 2** (точечно) | Entity cards по ID | Нужны детали конкретной сущности |

Это позволяет Pack работать при любом объёме — и при 30 файлах (context-loading), и при 300 (retrieval-based).

### Операционный цикл

| Операция | SOTA-практика |
|----------|---------------|
| Создание Pack | DDD Strategic — BC identification, UL extraction |
| Извлечение знаний | AI-Accelerated OE — LLM первый проход, человек валидирует |
| Capture на рубежах | Real-Time KM — не после сессии, а в момент работы |
| Контекст агента | Context Engineering (Write/Select/Compress/Isolate) |
| Поиск по Pack | Hybrid Retrieval — vector (summary) + точный (ID-коды) |

## Что НЕ применимо и почему

| Практика | Почему не подходит |
|----------|--------------------|
| Тактический DDD (Entity, Aggregate, VO) | ООП-специфика, не универсальна вне Java/C# |
| Full GraphRAG (Microsoft) | Избыточен для структурированного Pack |
| Статические `_index.md` | Устаревают так же, как ручной MAP — нужна генерация |

## Итог для практики

Если вы создаёте Pack:
1. Bounded Context — используйте DDD Strategic как операционализацию
2. Frontmatter каждой entity card — добавьте `summary` (≤150 символов) для retrieval
3. Связи — типизируйте: `produces`, `uses`, `fails_with` вместо плоского списка
4. MAP — генерируйте автоматически, не ведите руками
