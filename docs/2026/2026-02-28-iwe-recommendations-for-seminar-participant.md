### Разбор и рекомендации

#### Проблема не в хранении, а в фокусе

Участник говорит: «ничего не теряется, кроме фокуса. Брожу по записям, а не по мыслям.» Это ключевой симптом: хранилище есть, а навигационного слоя нет.

OneNote и Singularity — это то, что называют «second brain»: пассивное хранение. Знания записаны, но они не работают на тебя — ты сам должен каждый раз вспоминать, что искать, зачем, и куда это встроить в текущую работу.

IWE устроена иначе. Среда **сама возвращает в фокус**. Конкретный механизм — WP Gate: каждая рабочая сессия начинается не с блуждания по записям, а с привязки к конкретному рабочему продукту. Это как GPS для интеллектуальной работы — ты всегда знаешь, где ты и куда едешь.

#### Как связать цикл Цель → Метод → Действие → РП → Коррекция → Обновлённая цель

Это правильный вопрос. В IWE этот цикл уже реализован конкретными сервисами:

| Этап цикла | Что делает IWE | Как |
|------------|---------------|-----|
| **Цель** | WeekPlan / DayPlan | ИИ-Стратег формирует план на неделю/день |
| **Метод** | Протоколы работы | Для каждого типа задачи есть описание метода |
| **Действие** | Рабочая сессия | Три стадии: Открытие → Работа → Закрытие |
| **Рабочий продукт** | Конкретный артефакт | Задачи, планы, программы, презентации |
| **Коррекция** | Evening / Week Review | ИИ сравнивает план и факт, выявляет расхождения |
| **Обновлённая цель** | Session Prep | Автоматическая корректировка приоритетов |

Цикл связывается не вручную (тогда он развалится через неделю), а **средой**. Среда сама замыкает петлю обратной связи. Каждое звено — не абстракция, а конкретный сервис, который запускается автоматически или по запросу.

И вот зачем это нужно связывать: без замкнутого цикла цель живёт отдельно от работы. Ты планируешь одно, делаешь другое, а через неделю обнаруживаешь, что фокус уплыл. Замкнутый цикл — это механизм удержания фокуса, который у участника и является главной проблемой.

#### Не секретарь, а три роли

Участник спрашивает: «Это мой ИИ-секретарь или кто?» Не секретарь. Секретарь — это помощник по текучке. В IWE определены три ключевые ИИ-роли:

**Стратег** — планирует, ревьюит, корректирует. Решает главную проблему участника — возвращает фокус, напоминает приоритеты, выявляет отклонения от плана. Это не «напомни мне встречу», а «ты третий день делаешь не то, что запланировал на неделю».

**Экстрактор** — вытаскивает знания из рабочих сессий и записывает структурированно. Участник уже делает это с совещаниями (списки проблем, решений, инструментов). IWE формализует и автоматизирует — из стихийного извлечения делает систематическое накопление.

**Консультант** — отвечает на вопросы по накопленным знаниям. Если участник ведёт тренинги и готовит программы, консультант может работать с его собственной базой знаний.

Рекомендация: начать со **Стратега** — это даёт максимальный рычаг при проблеме с фокусом. Экстрактор вторым — потому что участник уже извлекает контекст из совещаний и понимает ценность этого.

#### Сильные стороны

1. Уже производит реальные рабочие продукты (программы тренингов, презентации, документы) — это не теория, а практика
2. Уже использует ИИ осмысленно (извлечение из совещаний) — не нужно убеждать в ценности
3. Хранит всё, что записал — дисциплина записи есть, нужна дисциплина **применения**

#### Следующий шаг

1. Попробовать бота — 5 минут, /start, посмотреть как работает
2. Первый эксперимент: взять одну задачу (подготовка программы тренинга) и пройти цикл Цель → Метод → РП → Коррекция с ИИ-помощником
3. Если зацепит — перейти к персонализации (цифровой двойник, стандартная методология)

### Разбор и рекомендации

#### Профиль одной строкой

IT-инфраструктурщик с широким стеком (ЦОД → сети → виртуализация → K8s → CI/CD → архитектура), уже работает в GitHub + Obsidian с FPF-подобной структурой. Проблема не в инструментах, а в **отсутствии слоя знаний** поверх слоя задач.

#### Диагноз по трём фактам

**Факт 1 — Область.** IT-инфраструктура с огромной «предметной ширью» (от BGP до GPU-нод в K8s). Это типичная проблема T-shaped специалиста: глубина в нескольких областях + необходимость ориентироваться во многих. IWE решает именно это — не запоминать всё, а **быстро восстанавливать контекст** через структурированные знания.

**Факт 2 — Симптом.** Теряются *сами знания* (как работает BGP, как создаётся VM в OpenStack). Это классический паттерн: человек разобрался → сделал задачу → через неделю знание «испарилось», потому что оно осталось **в голове или в чате**, а не в структурированном хранилище. У Владимира Б. теряется фокус. У Анатолия — само содержание. Разные болезни — разные лекарства.

**Факт 3 — ИИ.** Уже использует ИИ для архитектурных схем + документации. Это ровно тот рабочий продукт, который IWE поддерживает. Но без Pack эти схемы — одноразовые. С Pack — каждая схема становится **переиспользуемым знанием**.

#### Вопрос 1: Планирование дня и задач в GitHub

Да, и это одна из основных функций IWE. Вот как это устроено:

| Элемент | Как реализовано | Где живёт |
|---------|----------------|-----------|
| **Неделя** | WeekPlan — файл с приоритетами и бюджетом часов | `DS-my-strategy/current/` |
| **День** | DayPlan — автогенерируемый утром Стратегом | `DS-my-strategy/current/` |
| **Задача** | РП (рабочий продукт) с номером, статусом, контекстом | `MEMORY.md` + `inbox/WP-N-*.md` |
| **Метрики** | WakaTime (время) + Week Review (рефлексия) | Автоматически |
| **Обратная связь** | Стратег анализирует WakaTime + результаты еженедельно | `DS-my-strategy/current/` |

**Почему получается «монструозно или много источников»:** участник пытается решить задачу **одним инструментом** (таск-трекер ИЛИ заметки). IWE разделяет ответственность:
- **Governance** (что делать, приоритеты) → `DS-my-strategy/`
- **Работа** (как делать) → проектные DS-репо
- **Знания** (что узнал) → Pack

Три источника, но **один протокол** (ОРЗ: Открытие → Работа → Закрытие) и **один агент** (Стратег), который сводит. Человеку не нужно сводить вручную — среда делает это.

**Рекомендация:** начать с минимума — `MEMORY.md` (что на столе) + `CLAUDE.md` (как работаю) + один файл WeekPlan. Стратег-агент можно добавить позже. Первый месяц — привыкнуть к ОРЗ.

#### Вопрос 2: Как хранить теорию в экзокортексе

Это ключевой вопрос, и ответ — **Pack**.

Структура, которая у участника сейчас (Roles, Methods, Workplans, Work, Logs) — это **governance-слой** (управление деятельностью). А ему нужен **knowledge-слой** (управление знаниями). Это два разных слоя:

| Слой | Что хранит | Формат | У участника |
|------|-----------|--------|-------------|
| **Governance (DS)** | Задачи, планы, логи | Workplans, Logs | Есть, работает |
| **Knowledge (Pack)** | Теория, паттерны, различения | Сущности с ID и связями | **Нет — это и есть проблема** |

**Как бы выглядел Pack для IT-инфраструктуры:**

```
PACK-it-infrastructure/
  01-domain-contract/         ← различения и понятия
    INFRA.D.001-vm-vs-container.md
    INFRA.D.002-overlay-vs-underlay.md
  02-domain-entities/         ← ключевые сущности
    INFRA.NET.001-bgp-protocol.md       ← «как работает BGP»
    INFRA.VIRT.001-openstack-vm-lifecycle.md  ← «создание VM в OpenStack»
    INFRA.K8S.001-gpu-node-creation.md  ← «GPU-нода в K8s»
  03-methods/                 ← повторяемые методы
    INFRA.M.001-architecture-review.md
  04-architecture-patterns/   ← типовые решения
    INFRA.ARCH.001-network-fabric-design.md
```

Каждый файл — **одна единица знания** с кодом, описанием, связями. Не заметка. Не документ. **Сущность.**

Что это даёт:
1. **Через MCP** — ИИ-агент ищет по Pack напрямую. «Как создать GPU-ноду?» → находит `INFRA.K8S.001` → отвечает с опорой на ваши знания, а не на интернет.
2. **Через связи** — `INFRA.K8S.001` ссылается на `INFRA.VIRT.001` (виртуализация) и `INFRA.NET.001` (сеть). Знания не изолированы.
3. **Через Capture** — работаете с задачей (документация GPU-ноды) → на рубеже: «Capture: паттерн network policy для GPU workloads → INFRA.K8S.001». Знание фиксируется **в момент работы**, не «потом».

**Рекомендация:** начать с 5-10 сущностей по самым частым темам. Не описывать всё — описать то, что приходится **объяснять заново** каждые 2-3 недели. Именно это «испаряется через 3-7 дней». Claude поможет формализовать — покажите ему сырую заметку, скажите «оформи как Pack-сущность с ID и связями».

#### Сильные стороны

1. **Уже в Git + Obsidian** — нет барьера инструментов, только барьер формата
2. **FPF-подобная структура** — понимает зачем Roles, Methods, Workplans
3. **Мыслит письмом** — основной навык для Pack
4. **Работает с ИИ для архитектурных схем** — легко добавить Capture
5. **Рабочие продукты = документация** — идеально для Pack-конвейера

#### Следующий шаг

| Неделя | Шаг | Результат |
|--------|-----|-----------|
| **1** | Форкнуть шаблон IWE + заполнить MEMORY.md | Экзокортекс: ИИ помнит контекст |
| **2** | Первый Pack: 5 сущностей IT-инфраструктуры | Knowledge-слой: теория не теряется |
| **3** | Протокол ОРЗ + WP Gate | Governance: задачи в одном месте |
| **4** | Подключить MCP → ИИ ищет по Pack | Интеграция: ИИ использует ваши знания |

**Тир входа: T4** — уже готов к полной IWE (есть git, есть навык, есть потребность).

### Разбор и рекомендации

#### Профиль одной строкой

**Project Manager в FMCG** (продукты питания), ведёт параллельно множество проектов-запусков. Главная боль — потеря контекста при переключении между проектами и отсутствие приоритизации («все приоритеты высокие»). Инструменты фрагментированы (Obsidian + Word + Excel + таск-трекер).

#### Диагноз: три болезни одновременно

У предыдущих участников была одна главная проблема: у Владимира — фокус, у Анатолия — деградация знаний. У Юрия — **три проблемы сразу**, и они усиливают друг друга:

**Болезнь 1: Потеря мультипроектного контекста.** Вырезает слот под проект A → проект B «отпущен» → через неделю контекст по B улетел. Это не проблема памяти — это проблема **отсутствия контекстных файлов**. В IWE каждый проект имеет свой context file (`WP-N-*.md`), в котором зафиксировано: текущий статус, следующий шаг, открытые вопросы, принятые решения. Переключение = открыл файл → за 30 секунд восстановил контекст. ИИ делает это автоматически при открытии сессии (WP Gate).

**Болезнь 2: «Все приоритеты высокие».** Это классический симптом отсутствия governance-слоя. Если всё важно — ничего не важно. IWE решает через WeekPlan: Стратег-агент помогает расставить приоритеты на неделю, выделить 3-5 РП с конкретным бюджетом часов. Не «всё важное», а «вот эти три — на этой неделе, остальные — ждут». DayPlan утром конкретизирует: «сегодня — проект A, 4 часа; проект C, 2 часа».

**Болезнь 3: Фрагментация инструментов.** Obsidian + Word + Excel + таск-трекер = четыре источника, каждый с частью картины. Участник сам говорит: «интеграторская работа — склеить ужа с ежом». IWE не устраняет все инструменты (таск-трекер у команды останется), но даёт **единый интерфейс для PM**: вся *его* работа — в Git-репо, а взаимодействие с командой — через экспорт.

#### Вопрос 1: Планирование + экспорт для коллег

В IWE планирование живёт в Git-репозитории (`DS-my-strategy/`). Но Юрий справедливо замечает: коллеги не в его среде. Решение — **двухслойное**:

| Слой | Для кого | Где | Формат |
|------|---------|-----|--------|
| **Личный** | PM (Юрий) | Git-репо, MEMORY.md, WeekPlan | Markdown |
| **Командный** | Коллеги | Таск-трекер (существующий) | Задачи, CSV, что привычно |

Экспорт из Git в CSV — тривиальный скрипт. Markdown-файлы с YAML-frontmatter (статус, приоритет, ответственный) → `grep` + `awk` → CSV за секунду. Или Claude Code генерирует отчёт по запросу: «Собери статус по всем проектам в таблицу».

Важный принцип: **IWE — персональная среда PM, а не замена командного таск-трекера**. Юрию не нужно затаскивать коллег в Git. Ему нужно, чтобы *его* картина мира была целостной, а с командой он синхронизирует через привычные им каналы.

#### Вопрос 2: «Какой статус по проекту и следующий шаг?»

Это решается **контекстными файлами** — ядро IWE для мультипроектной работы:

```
DS-my-strategy/inbox/
  WP-01-product-launch-cheese-x.md    ← проект запуска сыра X
  WP-02-product-launch-yogurt-y.md    ← проект запуска йогурта Y
  WP-03-ops-improvement-logistics.md  ← проект оптимизации логистики
```

Каждый файл содержит:
- **Статус** — одна строка: где мы сейчас
- **Следующий шаг** — конкретное действие
- **Открытые вопросы** — что блокирует
- **Принятые решения** — что уже согласовано (лог решений)
- **Стейкхолдеры** — кто должен что сделать

При открытии сессии Claude читает MEMORY.md → видит проект → подгружает контекстный файл. Вопрос «какой статус по проекту X?» — не в голову, а в файл. ИИ отвечает за секунду.

При закрытии сессии (протокол Close) — контекстный файл обновляется автоматически. Следующая сессия начинается не с нуля.

#### Вопрос 3: Версионирование рецептур и экспериментов

Это самый интересный запрос — и Git решает его **нативно**. Рецептура продукта = конфигурация. Выработка/эксперимент = версия. Git создан именно для этого:

```
DS-product-launches/
  products/
    cheese-x/
      recipe-v1.md          ← базовая рецептура
      recipe-v2.md          ← после эксперимента #3
      experiments/
        exp-001-temp-change.md   ← изменили температуру
        exp-002-additive-test.md ← добавили компонент
      decisions.md           ← лог решений по продукту
    yogurt-y/
      ...
```

| Что даёт Git | Аналогия из производства |
|-------------|------------------------|
| **История изменений** | Каждая правка рецептуры — с датой и причиной |
| **Диффы** | «Чем v2 отличается от v1?» — видно построчно |
| **Ветки** | Параллельные эксперименты, не мешающие друг другу |
| **Откат** | «Вернуть рецептуру на версию до эксперимента #3» |
| **Теги** | Отметка «это пошло в производство» (release) |

Управление конфигурацией рецептур через Git — не «костыли», а **правильный инструмент**. Git был создан для версионирования текстовых файлов. Рецептура в markdown — текстовый файл. Всё сходится.

#### Уникальность профиля: РП = решение, а не документ

Юрий описывает свой РП необычно: «убеждённые начальники и понимающие коллеги». Это не документ, не схема, не код — это **сдвинутый кейс**. Но за каждым сдвигом стоят конкретные артефакты:

| Что сдвинулось | Какой артефакт фиксирует |
|---------------|------------------------|
| Начальник убеждён → ресурсы выделены | **Лог решений** (decisions.md) |
| Команда поняла → делает | **Следующий шаг** в контекстном файле |
| Гейт пройден | **Чеклист гейта** + статус в MEMORY.md |

IWE поможет Юрию не просто «помнить», а **накапливать паттерны убеждения**: какие аргументы сработали, какие нет, какие данные нужны для прохождения гейта. Это знания PM-а, которые обычно остаются в голове.

#### Сильные стороны

1. **Уже в Obsidian** — знает markdown, переход в Git минимален
2. **Осознаёт проблему фрагментации** — «склеить ужа с ежом» — значит, готов к единой среде
3. **PM-мышление** — думает в проектах, статусах, следующих шагах — IWE именно так и устроена
4. **Практик** — не теоретизирует, а «затаскивает» — сразу будет использовать по назначению
5. **Запрос на экспорт** — правильная забота: не ломать среду команды, а интегрироваться

#### Следующий шаг

| Неделя | Шаг | Результат |
|--------|-----|-----------|
| **1** | Форкнуть шаблон IWE + MEMORY.md с 3-5 текущими проектами | Единая картина: все проекты видны |
| **2** | Создать контекстные файлы по каждому проекту (статус + следующий шаг) | Переключение между проектами за 30 сек |
| **3** | Первый WeekPlan: приоритизировать проекты на неделю | Конец «все приоритеты высокие» |
| **4** | Один продукт перевести на Git-версионирование рецептуры | Управление конфигурацией работает |

**Тир входа: T3→T4.** Obsidian есть, Git — новый навык, но мотивация сильная (версионирование рецептур + мультипроектный контекст). Рекомендуем начать с бота (T3) для быстрых заметок и `/plan`, параллельно осваивая Git для версионирования.

#### Профиль одной строкой

#### Диагноз: ловушка GPT-чатов

Анастасия — первый участник, который точно описывает все три проблемы со слайда семинара:

| Проблема из семинара | Как проявляется у Анастасии |
|---------------------|---------------------------|
| **Амнезия** | «Даже в рамках одного чата многое теряется» |
| **Безструктурность** | «Много файлов в Notion, надо копировать вручную» |
| **Реактивность** | «Ассистент-стратег предлагает исправить только bottleneck» |

Но есть **четвёртая проблема**, уникальная для неё: **разрыв между рабочей и личной средой**. На работе — Claude Code в IDE, Git, структура. В личном — чаты GPT + Notion + ручное копирование. Это как если бы хирург оперировал с идеальными инструментами в клинике, а дома резал хлеб тупым ножом.

Причина разрыва понятна: рабочая среда настроена командой/компанией, а личную нужно настраивать самой. IWE — это именно инструмент, чтобы перенести рабочий уровень организации на личные проекты.

#### Вопрос 1: Как стратегирование учитывает все проекты, а не только bottleneck

Проблема с GPT-стратегом: у него **нет полной картины**. Каждый чат — изолированная сессия. Стратег видит только то, что вы вспомнили сказать в этом чате. Поэтому он «латает» bottleneck — это единственное, что он может предложить с ограниченным контекстом.

В IWE Стратег работает иначе:

| GPT-стратег (чат) | IWE-стратег (экзокортекс) |
|-------------------|--------------------------|
| Видит только текущий чат | Читает MEMORY.md → **все** проекты, статусы, бюджет |
| Каждая сессия с нуля | Знает историю: что было на прошлой неделе, что сдвинулось |
| Предлагает bottleneck | Видит **всю систему**: конфликты ресурсов, зависимости, дисбаланс |
| Не измеряет прогресс | WakaTime + Week Review = реальные цифры |

Конкретный механизм: WeekPlan содержит **все** проекты с приоритетами и бюджетом часов. Стратег при формировании плана учитывает:
- Какие проекты двигались на этой неделе, какие стояли
- Где deadline, где можно подождать
- Сколько часов реально потрачено (WakaTime) vs план
- Какие РП в каждом проекте ожидаются

Это не «исправь bottleneck» — это **полная картина** с расстановкой приоритетов.

#### Вопрос 2: Много проектов — можно ли?

Да, IWE не ограничивает тематику. Вот как это выглядит:

```
DS-my-strategy/          ← governance: планы, приоритеты
  current/
    WeekPlan-W10.md      ← все проекты одного взгляда
    DayPlan-2026-02-28.md

DS-creative-project-A/   ← творческий проект A
DS-learning-design/      ← обучение дизайну
DS-personal-blog/        ← блог / контент
```

В MEMORY.md — таблица всех активных РП:

```markdown
| # | РП | Статус |
|---|-----|--------|
| 1 | Творческий проект A: концепция | in_progress |
| 2 | Курс по 3D: модуль 3 | in_progress |
| 3 | Блог: статья про UX | pending |
```

Стратег видит всё. Приоритизирует. Человек решает.

#### Вопрос 3: Заметки в среде или в Notion?

**В среде.** Вот почему:

| Критерий | Notion | IWE (Git + бот) |
|----------|--------|----------------|
| Ввод | Быстрый (UI) | Быстрый (`.заметка` в боте) |
| Структура | Ручная (папки, базы) | Автоматическая (протокол Capture) |
| ИИ-доступ | Notion AI (ограничен) | Claude Code читает напрямую |
| Версионирование | Нет (30 дней истории) | Git: полная история навсегда |
| Экспорт | Markdown (ручной) | Уже markdown |
| Изображения | Встроены | В репо (Git) или ссылки |

**Про изображения и видео:** Git хорошо хранит текст. Для изображений — два подхода:
1. **Лёгкие** (скриншоты, схемы) → прямо в репо, в папке `assets/`
2. **Тяжёлые** (видео, PSD, Figma) → ссылки в markdown на облачное хранилище (Google Drive, Figma)

Figma-проекты остаются в Figma — это правильный инструмент для дизайна. Но **решения, выводы, паттерны** из дизайн-работы фиксируются в Pack (текстом) и становятся доступны ИИ.

#### Вопрос 4: Один репозиторий или несколько?

**Несколько.** В IWE каждый репозиторий имеет свой тип и назначение:

| Репо | Тип | Что содержит |
|------|-----|-------------|
| `DS-my-strategy` | DS/governance | Планы, WeekPlan, DayPlan, inbox |
| `DS-creative-project-A` | DS/surface | Конкретный проект |
| `PACK-design` | Pack | Знания о дизайне: паттерны, принципы, методы |
| Шаблон IWE (форк) | Template | CLAUDE.md, memory/, протоколы |

Принцип: **один проект = один DS-репо. Один домен знаний = один Pack.** Governance (стратегия) — отдельно.

Это не «раздувание». Каждый репо маленький, сфокусированный. Claude Code переключается между ними мгновенно.

#### Вопрос 5: Телефон

**Бот @aist_me_bot** — именно для этого. Всё, что нужно с телефона:

| Действие | Как |
|----------|-----|
| Быстрая заметка | `.мысль про проект A` — 3 секунды |
| План дня | `/plan` — синхронизирован с WeekPlan |
| Вопрос по знаниям | `?какой статус по проекту A` |
| Тест по изучаемому | `/test` |

VS Code на телефоне не нужен. Телефон = **быстрый ввод и просмотр**. Глубокая работа — за компьютером.

Записи в тетрадях и заметках, разрозненные исследования в Perplexity, сборки в Claude Code и Antigravity.

**Вопрос к демо:**
Для каждого проекта собирать свою среду или как-то организовывать в одну?

### Разбор и рекомендации

#### Профиль одной строкой

**Предприниматель с тремя несвязанными доменами** (профессиональное сообщество, телеком, коучинг/игры). Самая высокая фрагментация из всех участников — и по инструментам (тетради + Perplexity + Claude Code + Antigravity), и по доменам (три не пересекающиеся области).

#### Диагноз: мультидоменная фрагментация

У Юрия Б. — много проектов в одном домене (FMCG). У Алексея — **три совершенно разных домена**. Это качественно другая проблема:

| Участник | Проекты | Домены | Тип фрагментации |
|----------|---------|--------|------------------|
| Юрий Б. | Много | Один (FMCG) | Мультипроектная |
| Анастасия К. | Несколько | Два (работа + личное) | Контекстная |
| **Алексей Г.** | Три | **Три несвязанных** | **Мультидоменная** |

Мультидоменная фрагментация — самая тяжёлая. Каждый домен имеет свою терминологию, свои контакты, свои методы. Переключение между «ISP-сеть» и «трансформационная игра» — не просто смена проекта, это **смена мышления**.

При этом Алексей уже работает в Claude Code — значит, технический барьер минимален. Проблема не в инструментах, а в **отсутствии единого governance-слоя**, который бы связывал три мира.

#### Главный вопрос: одна среда или три?

**Ответ: одна среда, но несколько репозиториев.** Вот архитектура:

```
ОДНА среда (IWE)
├── DS-my-strategy/           ← ЕДИНЫЙ governance для ВСЕХ доменов
│   ├── MEMORY.md             ← все проекты, все статусы, одна таблица
│   ├── CLAUDE.md             ← общие правила работы
│   ├── current/
│   │   ├── WeekPlan-W10.md   ← приоритеты МЕЖДУ доменами
│   │   └── DayPlan.md        ← «сегодня: 3ч ISP, 2ч игра»
│   └── inbox/
│       ├── WP-01-club-*.md   ← контекст: клуб
│       ├── WP-02-isp-*.md    ← контекст: ISP
│       └── WP-03-game-*.md   ← контекст: игра
│
├── DS-professional-club/     ← проект: клуб
├── DS-isp-business/          ← проект: ISP
├── DS-transformation-game/   ← проект: игра
│
├── PACK-telecom/             ← знания: телеком (опционально)
└── PACK-coaching/            ← знания: коучинг (опционально)
```

**Почему одна среда, а не три:**

| Критерий | Три среды | Одна среда |
|----------|----------|------------|
| Приоритизация между доменами | Невозможна — каждая среда не знает о других | **WeekPlan видит всё** |
| Переключение | Переключение между средами | Переключение между контекстными файлами |
| Стратег | Три разных стратега, не координированных | **Один Стратег**, видит полную картину |
| Накладные расходы | x3 настройка, x3 обслуживание | x1 governance + маленькие DS-репо |

**Почему несколько репозиториев, а не один:**

Каждый домен — своя терминология, свои файлы, свой ритм. Смешивать код ISP-инфраструктуры с дизайн-документом трансформационной игры — хаос. Репо разделяют **содержание**. Governance (DS-my-strategy) связывает **управление**.

Принцип из IWE: **governance — один, проекты — по домену, знания — по домену**.

#### Что решает «разрыв циклов на всех этапах»

«Разрывов циклов много на всех этапах» — это самый честный и точный диагноз из всех пяти участников. Разрывы происходят в трёх точках:

**Разрыв 1: Между доменами.** Поработал над клубом → переключился на ISP → забыл, где остановился в игре. Решение: **контекстные файлы** (WP-*.md). Каждый проект — файл с «где я, что дальше». Восстановление = 30 секунд.

**Разрыв 2: Внутри домена.** Начал задачу → отвлёкся → через 3 дня не помнишь контекст. Решение: **протокол ОРЗ**. Закрытие сессии фиксирует результат и следующий шаг. Открытие — подгружает.

**Разрыв 3: Между инструментами.** Идея в тетради → исследование в Perplexity → сборка в Claude Code → и ничего из этого не связано. Решение: **одна точка входа** (MEMORY.md + бот). Мысль из тетради → `.заметка` в боте → попадает в inbox → Стратег видит.

#### Тетради: оставить или убрать?

Тетради — не враг. Для некоторых людей физическое письмо = мышление. Вопрос не «бросить тетрадь», а **замкнуть цикл**: мысль из тетради должна попасть в систему.

Два варианта:
1. **Фото → бот.** Сфоткал страницу → отправил боту → ИИ распознаёт и раскладывает
2. **Вечерний ритуал.** 5 минут вечером: пролистать тетрадь → ключевые мысли → `.заметка` в бот

Perplexity-исследования — аналогично: результат ресёрча → краткий вывод → в контекстный файл проекта или в Pack.

#### Что с Antigravity?

Antigravity (AI-инструмент для сборки) + Claude Code = два ИИ-окружения. IWE не запрещает использовать несколько ИИ. Но **governance** должен быть один. Результаты из Antigravity → фиксируются в Git (commit, файл, заметка). Тогда Claude Code видит их при следующей сессии.

#### Сильные стороны

1. **Уже в Claude Code** — технический барьер нулевой
2. **Предпринимательское мышление** — привык управлять несколькими направлениями параллельно
3. **Точный диагноз** — «разрывы циклов на всех этапах» = понимает проблему
4. **Правильный вопрос** — «одна или три среды» = думает архитектурно
5. **Три домена** — самая амбициозная настройка из всех участников, но и самая ценная, если получится

#### Следующий шаг

| Неделя | Шаг | Результат |
|--------|-----|-----------|
| **1** | Форкнуть шаблон IWE + MEMORY.md со **всеми тремя** доменами | Единая картина: клуб + ISP + игра |
| **2** | Контекстные файлы по каждому проекту (статус + следующий шаг) | Переключение между доменами за 30 сек |

**Тир входа: T4.** Claude Code уже есть. Главная задача — не техническая, а **архитектурная**: правильно развести три домена по репо и связать единым governance.
