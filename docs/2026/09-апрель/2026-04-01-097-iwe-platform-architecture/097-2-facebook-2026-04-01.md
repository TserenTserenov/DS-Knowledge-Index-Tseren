Как устроена среда для интеллектуальной работы, которую мы строим

Несколько месяцев я строил для себя систему, которая превращает ИИ-ассистента из «одноразового собеседника» в полноценного напарника. Напарника, который знает мои проекты, мои принципы работы, мои прошлые решения. Который не начинает каждый разговор с чистого листа.

Теперь встал вопрос: как это сделать продуктом для тысяч людей? Причём для людей, которые никогда не откроют терминал.

Расскажу, какую архитектуру мы выбрали и почему именно такую.

---

ДВА МИРА, КОТОРЫЕ НЕ СОЕДИНЯЮТСЯ

Сейчас существуют два полюса -- и между ними пропасть.

Первый полюс: умные ИИ-ассистенты. Claude, GPT, Gemini. Они отвечают на вопросы, пишут код, суммируют документы. Но каждая сессия начинается с нуля. Ассистент не знает, чем ты занимаешься, какие решения принял три месяца назад, какие у тебя принципы работы. Ты объясняешь контекст заново. Каждый. Раз.

Это как если бы ты каждое утро приходил в офис -- а твой коллега забыл, кто ты такой.

Второй полюс: системы хранения знаний. Notion, Obsidian, Roam. Они накапливают информацию, но пассивны. Ты ищешь сам, применяешь сам, связываешь сам. Ни одна из этих систем не может сама предложить: «Слушай, ты же три недели назад принял решение X -- оно противоречит тому, что ты сейчас делаешь».

Большинство людей живут в одном из этих миров. У кого-то мощный ИИ, но без памяти. У кого-то отличная база знаний, но без интеллекта.

IWE (Intellectual Work Environment) -- это мост между ними.

---

ЧТО ТАКОЕ IWE

IWE -- не приложение и не набор файлов. Это конфигурация рабочей среды: протоколы работы, подключения к сервисам, персональные знания, роли ИИ-ассистентов.

Аналогия, которая мне нравится: IDE (среда разработки) -- это не твой код. Но без IDE код писать можно, а продуктивно работать -- нет. IWE -- это IDE для интеллектуальной работы. Среда, в которой твои знания и твои инструменты наконец работают вместе.

---

ТРИ УРОВНЯ АРХИТЕКТУРЫ

У нас получилась трёхуровневая схема. Каждый уровень делает своё:

[Иллюстрация: три уровня архитектуры IWE -- см. картинку к посту]

Уровень 1 -- Платформа Aisystant. Это серверная часть, которая поставляет знания и сервисы. Здесь живут:
-- Знания МИМ (методология системного мышления -- формализованная, структурированная)
-- IWE-шаблон (когда пользователь регистрируется, платформа автоматически создаёт ему личное пространство на GitHub)
-- Векторные представления (embeddings) документов пользователя, чтобы ИИ мог искать по смыслу, а не по ключевым словам
-- Три MCP-сервера: один для публичных знаний платформы (3300+ документов), один для цифрового двойника пользователя, один для личных знаний (Pack)

MCP Gateway -- сердце архитектуры. Единая точка подключения на mcp.aisystant.com. Это слой между платформой и агентом. Любой ИИ-ассистент (Claude, GPT, Gemini, что угодно) подключается к одному URL -- и получает полный контекст пользователя. С авторизацией, с изоляцией данных, с кэшированием.

Уровень 2 -- Личный IWE пользователя. Это репозитории на GitHub, которые принадлежат пользователю. Его заметки, планы, решения, доменные знания. Всё хранится у него -- мы не забираем данные. Платформа только индексирует их (создаёт embeddings), чтобы агент мог искать.

Уровень 3 -- Вендорские агенты. Claude, GPT, Gemini -- или любой новый агент, который появится через год. Все они подключаются через один и тот же Gateway и получают одинаковый контекст. Пользователь не привязан к одному вендору.

Ключевое разделение: данные (репозитории) живут у пользователя. Вычислительное (поиск, embeddings, агенты) -- на платформе. Это как email: письма на сервере, но ты можешь читать их через любой клиент.

---

ПОЧЕМУ GATEWAY, А НЕ ПРЯМОЕ ПОДКЛЮЧЕНИЕ

Альтернатива была: каждый пользователь поднимает свой MCP-сервер. Я сам так работаю -- через Claude Code в терминале. Это работает отлично, если ты разработчик.

Но для тысяч пользователей, которые занимаются интеллектуальной работой (а не программированием), это нереалистично.

Gateway решает проблему: один URL, авторизация через OAuth (как «Войти через Google»), никакой настройки. Пользователь подключает своего ИИ-ассистента -- и тот сразу знает контекст.

Внутри Gateway три MCP-сервера, каждый со своей зоной ответственности:

knowledge-mcp -- публичные знания платформы. Методология системного мышления, гайды, документация. Это знания, которые одинаковы для всех пользователей. Кэшируются агрессивно -- если данные не менялись, не нужно читать файлы заново.

digital-twin-mcp -- цифровой двойник пользователя. Данные о прогрессе, целях, компетенциях. Это как профиль, только гораздо глубже -- история решений, пройденные курсы, оценки.

personal-knowledge-mcp -- личные знания. Собственные Pack-репозитории пользователя, проиндексированные и доступные для семантического поиска. 1700+ документов в текущей реализации.

Когда агент делает запрос, Gateway отправляет его одновременно во все три сервера (fan-out), собирает ответы, ранжирует по релевантности и возвращает единый результат. Пользователь не знает, откуда пришёл ответ -- из публичной базы знаний, из его цифрового двойника или из его личных заметок. Он просто получает ответ, который учитывает всё.

---

ТРИ АРХИТЕКТУРНЫХ РЕШЕНИЯ

Мы проходили каждое решение через АрхГейт -- оценку по семи характеристикам (эффективность, масштабируемость, безопасность и другие). Три места потребовали явных решений.

Первое: когда пользователь обновляет свои файлы, его embeddings устаревают. Агент начинает отвечать на старых данных. Решение: при push в репозиторий GitHub отправляет webhook, система ставит задачу в очередь, и в течение 5 минут embeddings обновляются. Пользователь не думает об индексе -- он просто работает.

Для записи обратно в репо пользователя (например, чтобы агент мог сохранять заметки) используется GitHub App с временным токеном, который живёт 1 час. Никакие постоянные пароли не хранятся.

Второе: Gateway добавляет дополнительный шаг между агентом и данными. Это могло бы замедлить работу -- но мы поставили жёсткий SLA: задержка Gateway не больше 200 миллисекунд. Кэш обновляется по хэшу коммита: если репо не менялось -- ответ из кэша.

Третье: изоляция данных между пользователями. Все embeddings хранятся в одной базе (pgvector на Neon). Без защиты поиск пользователя A мог бы случайно найти данные пользователя B. Решение: фильтрация по user_id из JWT-токена (не из параметра запроса -- это исключает SQL-инъекцию по дизайну). Этого хватит до 30 тысяч пользователей. При росте -- миграция на Qdrant с отдельной коллекцией для каждого пользователя.

---

ФОРМАЛИЗОВАННЫЙ КОНТРАКТ

Чтобы Gateway масштабировался без ручной интеграции каждого нового источника данных, мы формализовали MCP-контракт. Каждый бэкенд реализует четыре метода и обязательный инструмент поиска с нормализованной оценкой релевантности.

Это открывает путь к BYOB (Bring Your Own Backend): в будущем пользователь сможет зарегистрировать свой собственный MCP-сервер, и Gateway подключит его без изменения платформенного кода. Компания может подключить свою внутреннюю базу знаний -- и агент будет искать в ней наряду с публичными знаниями.

Качество каждого бэкенда проверяется через Knowledge Gate -- 7 автоматических проверок при каждом деплое. Это как тесты для кода, только для качества знаний.

---

ЧТО ЭТО МЕНЯЕТ ДЛЯ ЧЕЛОВЕКА

Конкретный сценарий. Человек регистрируется на Aisystant. Платформа автоматически создаёт ему репозиторий на GitHub (форк готового шаблона IWE). Он начинает работать -- в боте, на сайте, в Claude Code. Записывает заметки, создаёт планы, фиксирует решения.

Через год у него в репо сотни файлов. Его принципы работы. Его доменные знания. Его история решений. Всё это -- его собственность. Не наша.

Теперь он подключает к этому репо GPT. Или Gemini. Или агент, который появится через два года и про который мы сейчас даже не знаем. Gateway узнаёт пользователя -- и любой агент получает полный контекст.

Его среда интеллектуальной работы переносима. Данные у него. Сервисы -- у нас. Если он решит уйти с платформы -- его знания останутся у него, в его GitHub. Это принципиальное решение.

---

ЧТО ДАЛЬШЕ

Gateway работает. Три MCP-сервера подключены, fan-out поиск и изоляция данных верифицированы. Следующие шаги:

LLM Proxy -- ИИ как сервис платформы. Роутинг запросов по моделям, учёт использования per user. Чтобы пользователю не нужен был собственный API-ключ для работы с ИИ.

Серверные агенты -- ИИ-ассистенты, работающие на стороне платформы. Сейчас агент работает на устройстве пользователя (в Claude Code, в боте). Серверные агенты позволят запускать длительные задачи на платформе -- анализ большого объёма данных, генерация отчётов, периодические проверки.

BYOB -- возможность подключения внешних MCP-серверов. Корпоративная база знаний, внутренний API, специализированный инструмент -- всё через единый Gateway.

Если интересна техническая детализация -- спрашивайте.
