# Как устроена среда для интеллектуальной работы: IWE как платформенный продукт с личным ядром знаний

Последние несколько месяцев я строю систему, которая превращает ИИ-ассистента из «одноразового собеседника» в полноценного напарника на всю жизнь. Напарника, который знает твои проекты, твои принципы работы, твои прошлые решения и который аккуратно собирает и формализует твой опыт. Строю сразу для людей -- не как личный эксперимент, а как продукт.

Главный вопрос архитектуры: как сделать это для тысяч пользователей? Причём для людей, которые никогда не откроют терминал.

Это пост о том, какую архитектуру мы выбрали, почему именно такую -- и что уже работает.

---

## Проблема: частичные решения с привязкой к вендору

Рынок уже движется в сторону «ИИ + знания». ChatGPT запоминает контекст между сессиями. Notion AI ищет по твоим документам. Claude Code работает с файлами инструкций и памятью. Проблема не в том, что никто этого не делает. Проблема в том, как это делается.

**Каждое решение привязано к одному вендору.** Память ChatGPT не особо перенести в Claude. Notion AI не работает за пределами Notion. Твои знания, протоколы, история решений -- заперты внутри одного продукта. Ты вкладываешь месяцы в настройку, а потом появляется новая модель -- и начинаешь с нуля. Ну и вендоры не охотно отдают твои знания.

**Память поверхностна.** Вендорские решения запоминают факты из разговоров. «Ты упоминал, что работаешь с DDD» -- это уровень визитки. А мне нужно, чтобы ассистент знал мою предметную область с 300 документами по доменной модели, мои архитектурные решения за последний год, мои формализованные принципы работы. Разница -- как между «мы знакомы» и «мы работаем вместе».

**Нет протоколов работы.** ИИ-ассистент отвечает на вопросы, но не встроен в рабочий процесс. Он не знает, что перед началом задачи нужно проверить план недели. Что архитектурное решение требует оценки по семи характеристикам. Что закрытие дня включает фиксацию результатов. Ассистент умный, но не дисциплинированный.

IWE -- это не ещё один ИИ-ассистент с памятью. Это **операционная система для интеллектуальной работы**: среда, в которой знания, протоколы и агенты работают вместе, и не привязаны к одному вендору.

---

## Что такое IWE в этой архитектуре

IWE -- не инструмент и не набор файлов. Это **конфигурация рабочей среды**: протоколы работы, подключения к сервисам, персональные знания, роли агентов.

Аналогия: IDE -- это не твой код. Но без IDE код писать можно, а работать -- нет. IWE -- IDE для интеллектуальной работы.

В архитектурном смысле у пользователя есть три уровня:

![Архитектура IWE: три уровня](https://raw.githubusercontent.com/TserenTserenov/DS-Knowledge-Index-Tseren/main/docs/2026/09-%D0%B0%D0%BF%D1%80%D0%B5%D0%BB%D1%8C/2026-04-01-097-iwe-platform-architecture/iwe-architecture.png)

**Ключевое разделение:** данные (репо) живут у пользователя, вычислительное (embeddings, поиск, агенты) -- на платформе.

---

## Что поставляет платформа

**Aisystant поставляет четыре вещи:**

**1. Знания МИМ.** Методология системного мышления -- формализованная, структурированная, готовая к использованию в контексте агента. Не просто тексты -- Pack-сущности с ID, frontmatter, связями.

**2. IWE-шаблон.** При регистрации платформа форкает `FMT-exocortex-template` в GitHub-пространство пользователя. Через OAuth, автоматически. Пользователь получает рабочую среду без настройки вручную.

**3. Embeddings личного Pack.** Пользователь работает в своём репо -- пишет заметки, создаёт Pack-документы, фиксирует решения. Платформа векторизует эти файлы и хранит embeddings. При запросе агент ищет по смыслу, а не по ключевым словам.

**4. MCP Gateway.** Единая точка подключения. Вендорский агент (Claude, GPT, любой другой) подключается к одному URL. Gateway знает, кто этот пользователь, и отдаёт правильный контекст: знания МИМ + личный Pack + протоколы.

---

## Почему Gateway, а не прямое подключение

Это архитектурное решение, которое кажется очевидным только после того, как видишь альтернативу.

Альтернатива: каждый пользователь поднимает свой MCP-сервер. Это работает для технарей (я сам так и работаю через Claude Code CLI). Но для массовой аудитории это барьер.

Gateway решает проблему: один URL, авторизация через OAuth, никакой настройки на стороне пользователя. При этом внутри Gateway -- три MCP-сервера:

- **knowledge-mcp** -- публичные знания платформы. Методология системного мышления, гайды, документация. Кэшируются агрессивно -- если данные не менялись, не нужно читать файлы заново. 16 источников, 3300+ документов.
- **digital-twin-mcp** -- цифровой двойник пользователя. Данные о прогрессе, целях, компетенциях. Это как профиль, только гораздо глубже -- история решений, пройденные курсы, оценки.
- **personal-knowledge-mcp** -- личные знания. Собственные Pack-репозитории пользователя, проиндексированные и доступные для семантического поиска. 1700+ документов в текущей реализации.

Когда агент делает запрос, Gateway отправляет его одновременно во все три сервера (fan-out), собирает ответы, ранжирует по релевантности и возвращает единый ответ.

## Три технических решения, прошедших АрхГейт

Мы проходили каждое решение через АрхГейт (ещё одно правило в IWE по архитектурному выбору) -- оценку по семи характеристикам (эффективность, масштабируемость, безопасность и другие). Три места потребовали явных решений.

**1. Переиндексация embeddings -- webhook-триггер.**

Проблема: пользователь обновил Pack-репо, embeddings устарели, агент отвечает на старом контексте.

Решение: push в репо, GitHub webhook, задача в очередь, асинхронная частичная переиндексация. Пользователь не думает об индексе. Задержка -- целевые не более 5 минут после push. Для записи обратно в репо пользователя -- GitHub App с installation token (TTL 1 час, без хранения credentials).

**2. Latency Gateway -- SLA + кэш.**

Gateway добавляет hop между агентом и данными. Без ограничений это чёрный ящик.

Решение: SLA не более 200ms на Gateway overhead. Кэш контекста инвалидируется по commit hash репо -- если Pack не менялся, отдаём из кэша без чтения файлов.

**3. Изоляция embeddings между пользователями -- namespace per user.**

Векторное хранилище мультитенантное. Без явной изоляции поиск пользователя A может затронуть данные пользователя B.

Решение: фильтр `WHERE user_id = $1` в pgvector (Neon). `user_id` берётся из JWT-токена (Ory), не из параметра запроса -- SQL-инъекция исключена по дизайну. Этого достаточно до примерно 30к пользователей. При росте -- миграция на Qdrant с collection per user.

## Формализованный контракт: ADR-IWE-003

Чтобы Gateway масштабировался без ручной интеграции каждого бэкенда, мы формализовали MCP-контракт (ADR-IWE-003). Каждый бэкенд реализует четыре метода: `initialize`, `tools/list`, `tools/call`, `ping`. Обязательный инструмент -- `search` с нормализованным score в диапазоне [0.0, 1.0].

Это открывает путь к BYOB (Bring Your Own Backend): пользователь сможет зарегистрировать свой MCP-сервер в Backend Registry, и Gateway подключит его без изменения платформенного кода.

Качество бэкендов проверяется через Knowledge Gate -- 7 автоматических проверок (KG-01..KG-07) при каждом деплое и 4 ручных (KG-10..KG-13) при добавлении нового источника.

---

## Что это меняет для пользователя

Конкретный сценарий: человек регистрируется на Aisystant. Платформа создаёт ему репо на GitHub (форк шаблона IWE). Он начинает работать -- в боте, на сайте, в Claude Code. Записывает заметки, создаёт планы, фиксирует решения.

Через год у него в репо -- сотни файлов. Его принципы работы. Его доменные знания. Его история решений.

Теперь он подключает к этому репо GPT. Или Gemini. Или любой новый агент, который появится через два года. Gateway знает этого пользователя -- и любой агент получает полный контекст.

Его IWE переносимо. Данные у него. Сервисы -- у нас.

## Что дальше

Gateway запущен — работает как Aisystant MCP. Три MCP-сервера подключены, fan-out поиск и изоляция данных верифицированы. Первая когорта пилотов использует Gateway через claude.ai. Следующие шаги:

- **Серверные агенты** -- агенты, работающие на стороне платформы через Gateway. Полный паритет T4 (все четыре уровня зрелости доступны через один интерфейс).
- **LLM Proxy** -- ИИ как сервис платформы: роутинг по моделям, учёт токенов per user. Чтобы пользователю не нужен был свой API-ключ.
- **BYOB** -- регистрация пользовательских MCP-серверов через Backend Registry.

Уверен, что многие идут по похожему пути и создают что-то подобное. Я со своей стороны ориентируюсь на системный подход третьего поколения и на первые принципы (FPF А. Левенчука) и свои наработки по методам саморазвития, культуры работы (они зашиты в IWE) и отдыха.

Если интересна техническая детализация -- спрашивайте. Или смотрите [DP.IWE.003](https://github.com/TserenTserenov/PACK-digital-platform/blob/main/pack/digital-platform/02-domain-entities/DP.IWE.003-gateway-architecture.md) -- там полная архитектурная спецификация.
